# 规格工作流

## 为什么有这套东西

2026-09-11 之前，这个仓库的规格和代码之间**没有任何机器可验证的连接**：追踪矩阵手工维护、规则改了没人提醒门要跟着改、文档搬家断链靠运气。三样都会无声失效。

同一天还发现，一次 507 文件的 checkpoint 提交（`72201ea`）改了已裁定行为并打掉 99 个单测，**两天没人知道**——因为 `npm test` 不含 `module:check`，而且当时没有 CI。

现在每条链接都有东西在喊。这个技能说明怎么在不破坏它们的前提下工作。

## 三类文件，分工固定

| 文件 | 回答什么 | 可变性 |
| --- | --- | --- |
| `docs/specs/` 的 SPEC | 规则**现在**是什么 | 就地改写；历史交给 git |
| `docs/adr/` 的 ADR | **为什么**这么定、何时定、取代了什么 | 一份决定一份，写完不再追加 |
| `docs/agent/receipts/` 的回执 | 当时**验到了**什么 | 一次性证据，不再修改 |

核心规则是**取代即编辑**。新决定改变旧规则时，直接改写 SPEC 里那一句，不在任何文件追加「某月某日又改成了什么」。

这条不是洁癖。追加式修订之前让「Proposal 到底能调几次模型」要拼装六个地方才能回答，每处还部分取代另外几处。ADR 0015 一份文件里积了 25 条日期追加，其中三条描述的产品行为**任何 SPEC 都没写**——决策记录在当规格用。

## 场景一：改需求或做出新裁定

```bash
npm run spec:trace
```

先看目标条款被哪些代码引用、哪些门守着。然后：

1. **改写那一条**，不追加。
2. 新建 ADR（编号顺延），记录日期、为什么、取代了什么，并**指向规则所在的条款**。ADR 不重述规则文本——重述的那份迟早和原件分岔。
3. 在该 SPEC frontmatter 的 `revisions` 加一行。
4. 在 `docs/specs/README.md` 的决定记录表加一行。
5. 改该条款 `gates` 所列的测试。
6. `npm run spec:check` 必须 0 错误。

### 必须先问用户的情况

按 `AGENTS.md` 的「产品需求与规格权威」，已批准或已裁定的 SPEC **默认不改**。只有用户明确要求的产品结果与具体条款实质冲突时，才指出冲突、影响和拟修改条款，提出一个最小确认问题，取得明确确认后才动。

用户没确认时：不改规格，也不实现与其冲突的行为。

### gates_verified_on 什么时候能盖

`stale-gate` 警告的含义是「规格正文比守着它的测试更新」。重构（搬条款、拆文件）会触发它，但规则没变。

这时可以在 frontmatter 写 `gates_verified_on: YYYY-MM-DD`，含义是**这天有人确认过这些门仍守着正确条款**。

**规则真的变了就去改门，不要盖章。** 盖章是把真问题藏起来。判断依据是：这次改动有没有改变任何一句规则文本。搬动、拆分、删重复元数据都没有；改一个数字、加一条约束都有。

## 场景二：修 Bug

按 `AGENTS.md` 的「Bug 修复闭环」走，另加两步：

1. 定位根因后，确认它违反的是哪一条 SPEC 条款，并**在修复的测试或代码里写上 `SPEC NNNN §x.y`**。

   这是 `spec-trace` 把条款和实现连起来的唯一方式。`SPEC 0007` 有 14 节、两个测试文件覆盖，但全项目没有一个文件写过 "SPEC 0007"，于是它在报告里显示为「未实现」——加两行注释就从 0 变成 8/14。

   引用可以写 `§7.1`、`section 8`、`6.1`、`21.I`、`F04`，也可以写 `§§1、2、5` 这样的列表（整串都会登记）。

2. 若该条款当前没有门（`spec-trace` 的 gates 列是 `—`），把本次回归测试填进该 SPEC 的 `gates`。

### 行为偏离已裁定 SPEC 时，默认是 Bug

不是规格过时。要改规格必须先走场景一的确认流程，**不得改测试制造表面一致**。

这条最容易在夹具上踩空。判断方法：如果产品收紧了某个不变量而夹具没跟上，修夹具是对的（夹具本来就不自洽）；如果产品改变了可观察行为而没有 SPEC 修订或 ADR，那是悬空态，先确认再动。

例：`spendCosts` 加了「玩家资源池必须由角色档案背书」，夹具只设了战斗实体的池——这是夹具不自洽，修夹具。同一次提交把反制资格改成只认冻结注册操作，导致所有手写定义作废——这是行为变更，没有记录，需要裁定。

### 声明一个门之前先跑它

红的门比没有门更糟：它让 `spec:check` 长期红，然后所有人开始无视整个报告。

`npm run gates:check` 会真的运行每个声明的门：基线之外的红门直接失败，刚声明、从没见过绿的门也算红。声明门的同一次提交里先跑它。

怎么选门：看测试标题是否直接断言该条款要求的行为。`kp-vnext-narration` 有一项叫 `passing reviews carry no per-fragment or per-fact proof`，那就是 §8.3 的门。只是在注释里提了一句 SPEC 编号的测试**不是**门——`inventory-operations-vnext` 引用了 0013 但测的是背包操作。

## 场景三：拆分或搬动规格文件

条款编号不变，代码引用就不会断。

- 主文件保留 frontmatter、前几节与分册索引，`parts:` 列出分册。
- 分册 frontmatter 写 `kind: part`、`part_of: "00NN"`、`clauses: "4-6"`。
- 非规范内容（自主裁定记录、实现映射、交叉审查、实施完成门、开发期回执）移到 `kind: annex` 的附录文件，**原位留标题和一行指针**，这样 `§13` 仍然解析得到。
- 覆盖检查：分册区间必须覆盖所有节。曾经因为最后一个区间写成 `9-13` 而漏掉 `§14`，条款数从 34 掉到 33。

### 删任何散文之前先核实

搬走一段规则之前，确认它声称的规则**已经在 SPEC 正文里**。方法是提取关键词到全部 spec 文本里搜。

README 的十段日期散文全部核实过在正文里才删的——所以那次是纯去重，没有丢规则。ADR 0015 的三条没通过核实，于是没删，而是先写成条款。

搬完必须跑链接检查：一次日志拆分让 63 条链接失效，因为条目里的 `](agent/foo.md)` 是相对 `docs/` 写的。

## 工具

```bash
npm run spec:check   # 硬门：引用不存在的规格或条款即失败
npm run spec:trace   # 完整报告：字数、条款、引用、门、警告
npm run gate         # 棘轮：边界违规与断链，不含单测
npm run gates:check  # 运行各 SPEC 声明的门（Node 与 Worker），按文件和失败用例名棘轮
```

```bash
node tools/check-doc-links.mjs --baseline
```

编辑 `docs/specs/**` 或任何 `docs/**/*.md` 后，`.claude/settings.json` 的 PostToolUse 钩子会自动跑前两项，成功静默、失败退出 2。所以多数情况不需要手动跑。

### 棘轮怎么用

`.gate-baseline.json` 记的是**违规原文和失败用例名**，不是数量——修好一个又弄坏另一个骗不过它。修好之后：

```bash
node tools/gate.mjs --with-tests --update
```

`--update` 写交集，只删不增。**回归必须修，不能登记。**

唯一例外是提案请求体积（`requestSize`）：为合理的功能加提示词时，先告诉用户加什么、各选择多多少 token，再在同一次提交里运行 `node tools/gate.mjs --accept-request-size`；新文字不能重复提示词已有的内容（ADR 0057）。

## 不要做的事

- 不要为了让检查变绿而扩 `check-modules` 的 allowlist，或往基线里登记新违规。那是把裁定伪装成配置。
- 不要在 ADR 或 README 里追加「某月某日又改成了什么」。
- 不要声明一个没跑过的门。
- 不要在规则真变了的时候盖 `gates_verified_on`。
- 不要把产品行为只写在 ADR 里。ADR 记为什么，SPEC 记是什么。
