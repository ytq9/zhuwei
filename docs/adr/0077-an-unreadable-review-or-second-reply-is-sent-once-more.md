# ADR 0077：读不出的审核回复和 NPC 第二次作答，同一请求重发一次

- 状态：已接受
- 日期：2026-09-30
- 依据：本地预览故障 [ZW-munycxry](../agent/receipts/incident-munycxry-20260930.md)。用户看过排查结果后，在“同一请求重发一次”和“保持技术失败”之间选择前者，并决定由 Claude 在主工作区修改。
- 当前规则：[SPEC 0016 §7.2](../specs/0016-part-c-compound-actions-and-claims.md)。
- 取代范围：
  - [ADR 0076](0076-review-npc-replies-and-admit-experiences-with-knowledge.md) 与 SPEC 0016 §7.2 原先的“审核响应格式或绑定错误直接技术失败”。
  - [ADR 0073](0073-an-npc-writes-its-own-reply-from-its-own-view.md) 中“同一份回答只重问一次，仍不通过时行动以技术失败结束”对读不出的第二次作答的适用。
  - ADR 0076 定的审核序号 139–146 改为 139–154。

## 原因

用户在本地预览里连续两次行动失败，两次都发生在回答审核把莉安的回答退回之后：

- 第一次：第二次审核批准了莉安标为 `reported` 的两条内容，代码只允许批准 `believed`，整份审核被判无效。
- 第二次（ZW-munycxry）：莉安的第二次作答把五个字段各写了两遍，还多出一个表单没有的字段，读不出来。

两个请求都声明了 strict 表单。对 9 月 22 日以来保存的全部 strict 调用逐次核对，简单表单（选择、旁白审核、修订）没有违规，复杂表单时常违规：裁决填写 17/48、NPC 作答 2/18、回答审核 1/11。这种情况从现有证据最早的一天起就存在，不是服务商在某一天改变了行为。

裁决填写有三轮修订兜底。审核和 NPC 第二次作答原先没有任何补救，只要回复格式坏了，行动就按技术失败结束。审核每退回一次，就多一次这样的机会。下午用同一版代码进行的 4 次交谈里有 2 次这样失败。

## 决定

1. 重问得到的 NPC 回答读不出或不合作答表单时，同一请求重发一次。重发用第二次请求原来的字节，票据加 `resend` 标记。重发不是又一次重问；再读不出就技术失败。第二次回答读出来了、但在其他方面不合格时，不重发，照旧技术失败。
2. 审核回复读不出、不合审核表单，或与所审的回答和条目对不上时，同一请求重发一次。请求里的审核票据不带重发标记，所以两次请求字节相同。重发不算审核阶段；再不可用就技术失败。
3. 是否重发由 Room 从保存的请求和响应判断，与适配器共用同一个结算函数。模型不能自报重发资格。
4. 每份裁决版本的审核最多两阶段、每阶段最多发两次，四份裁决版本最多 16 次，审核序号改为 139–154。已有房间里约束为 1–138 或 1–146 的阶段记录表，在 Durable Object 启动时原地重建，保留全部记录。

同时修正了两处实现缺陷，它们落实的是已有规则，不是新的裁定：

- NPC 作答表单为 `attitude` 的四个值写明含义：亲身经历或确信为真、从别人那里听来、自己也拿不准、明知不实仍这么说。
- 审核请求为每条条目列出可选的结论，只有 `believed` 的条目可以 `approve`；读取时按同一张表核对。

## 影响

- 只在回复格式出错时多一次调用。已有真实调用的输入规模：审核 2.7 万至 3.4 万 token，NPC 第二次作答约 1.5 万。重发的请求与原请求字节相同，可能命中缓存，本次没有实测。
- NPC 作答请求因 `attitude` 说明多约 60 个估算 token；审核请求没有条目时多约 10 个，每条条目再多约 20 个。按 ZW-munycxry 所在房间的两次行动离线重建测得。
- NPC 作答策略升为 `zhuwei.npc-reply/v3`，审核策略升为 `zhuwei.npc-reply-review/v6`。尚未冻结的方案按 SPEC 0016 §9.2 在新版本下重问。
- 按“原因”一节的违规比例粗算，一次交谈因回复格式失败的机会从一成左右降到百分之一二。样本少，只能作为量级参考，需要真实批次确认。
- 服务商为什么在 strict 模式下仍返回不合表单的参数，没有查明。
