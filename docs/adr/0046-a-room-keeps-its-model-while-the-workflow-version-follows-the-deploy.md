# ADR 0046：房间固定所用模型，工作流版本随部署更新

- 状态：已接受
- 日期：2026-09-25
- 依据：房间建桌时把整套 KP 工作流清单写进房间记录，清单里含提示、schema、解析器和传输的版本 hash；服务端只接受与当前代码逐字相同的清单。于是每次改提示，已有房间都进不去。本地预览里，房间 `Q6ACEG` 建于指引 v44，指引改到 v46 后进房被拒，提示“本桌绑定的权威 KP 模型 Profile 已不可用”；2026-09-10 的线上发布也因此让一桌不能续玩。这与 [SPEC 0016 §9.2](../specs/0016-part-d-staging-and-supersede.md) 和 [ADR 0038](0038-reask-unfinished-work-after-a-version-change.md) 的前提矛盾：那里假定部署改了提示后房间照常继续，只把未冻结的工作重问一轮。用户确认按新条款处理。
- 当前规则：[SPEC 0011 §3](../specs/0011-reliability-correction-observability-and-evaluation.md)
- 取代范围：SPEC 0011 §3 原句“房间创建后固定，重启、归档恢复和历史分支继续使用原绑定”中连工作流版本一起固定的含义，以及 `roomRuntimeConfiguration()` 只接受逐字相同清单的做法。

## 决定

1. 房间按所用模型核对。房间记录的工作流清单必须是服务端原样写出的 JSON，它的 `workflowRef`、KP Profile 和旁白 Profile 与当前某个模型配置一致即可；提示、schema、解析器、传输等版本字段可以不同。换模型、换 Profile 或换旁白 Profile 仍然拒绝。
2. 进房、单人与多人行动、更正、重试旁白和历史分支都经过 `roomRuntimeConfiguration()` 的同一个判断。房间对象本来只记模型，每次按当前代码里该模型的配置运行，不需要改动。
3. 单人与多人行动在核对通过后，把房间记录的清单更新为当前版本。更新时比较旧值再写入，并发的两次行动只会写一次。
4. 未冻结的工作按 ADR 0038 重问一轮，不变。

## 后果

- 改提示或 schema 后可以直接部署，已有房间仍能进入和继续。
- 规则运行时的绑定不在本决定内：房间状态里的 runtimeProfiles 仍须与当前清单一致（[SPEC 0013](../specs/0013-versioned-runtime-profiles.md)）。
- 未覆盖：归档校验现在用当前代码重建每次调用的请求，证明裁决出自那次回复。早先版本的调用无法这样重建，所以这类房间从归档恢复或建历史分支仍会失败。SPEC 0011 §3 要求按记录的版本核对；这一步涉及防伪造归档的取舍，另行决定和实现。
