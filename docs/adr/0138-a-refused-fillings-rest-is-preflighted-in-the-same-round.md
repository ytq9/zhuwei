# ADR 0138：本地被拒的填写，其余部分在同一轮预检

- 状态：已接受
- 日期：2026-10-10
- 依据：[物品引用审计](../../tests/kp/items/item-reference-audit.test.mjs)在 [ADR 0135](0135-every-refused-step-is-reported-at-its-field-with-candidates.md)、[ADR 0136](0136-a-holder-remembers-how-each-loose-stack-came-to-hand.md) 之后只剩 2 个缺口：取放声明被本地拒绝时，另一步里只有降级或 Rules 才能发现的错误要等下一轮。补测 4 个组合后确认这是一类问题：只要有一步被本地检查拒绝（数量为 0、漏写 kind、取放声明出错），整份稿子都不做降级和 Rules 预检。修订最多 3 轮，晚一轮报出就多一次调用，也可能把轮数用完。用户批准方案，并确认修改 SPEC 0016 §7.2 的措辞。
- 当前规则：[SPEC 0016 §7.2](../specs/0016-part-c-compound-actions-and-claims.md)（本次修订）；延续 [ADR 0095](0095-one-revision-lists-every-problem.md)"一次修订列出全部问题"。

## 决定

1. **拆出其余部分。** 本地被拒的工单（表单、依赖或线上格式错误）由 `vnextProposalStandIn` 从模型原稿里去掉：
   - 被拒的行；
   - 与这些行相关的行。

   "相关"按引用判断，并递推到不再变化为止：被去掉的行会改变某些对象，用到这些对象的行也去掉。
   - 普通的取、放、丢、交只改变被移动的物品。容器没有容量限制，所以不算改变容器。
   - 取放声明还会开合容器，所以也算改变容器。
   - 其他种类的行，算改变它点名的所有对象，但不包括它引用的依据、观察者和场景。

   以下情况不预检，和以前一样：
   - 问题不在某一行上；
   - 决定是澄清；
   - 去掉之后什么都不剩；
   - 剩下的方案过不了本地检查；
   - 剩下的方案需要 NPC 回答。
2. **Room 预检其余部分。** 适配器通过 `preflightStandInForAction` 请 Room 做降级和 Rules 预检。这和 Room 对完整方案的预检是同一个方法（`proposalPreflight`）：不掷骰，不写事件，不保存任何东西。
3. **同一张工单。** 预检诊断追加在本地诊断之后，路径换算回模型原稿里的行，修订提示把两类问题一起发给模型（`vnextProposalStandInTicket`）。工单字段不变。`assertRepairTicket` 要求本地诊断一项不差地排在前面，追加的每一项都落在 `steps` 或 `check` 的某一行上。
4. **Room 证明。** 调用开始时，Room 对当前这一轮自己重做一遍部分预检，结果必须与请求中的工单一致；更早的轮次用当时保存的工单（`vnextProposalTicketWithSavedPreflight`）；恢复中的调用沿用已保存的工单。调用方给出的诊断不能单独授予修订。
5. **只列诊断，不判结果。** 部分预检的结果只写进修订工单。修订后的整份方案仍然完整校验和预检。
6. 解析合同升为 v93。运行版本、事件格式和上下文版本不变。按 [ADR 0038](0038-reask-unfinished-work-after-a-version-change.md)，正在修订中的行动重问一轮。

## 后果

- 不增加模型调用。每个本地被拒、且能拆出其余部分的轮次，多一次 Worker 到 Room 的调用，以及 Room 内的一次降级和一次 Rules 预检。
- 与被拒行相关的行仍要晚一轮才报错。这样做是为了不报出因为去掉步骤而产生的假错误，审计里有对照覆盖这一点。
- 适配器调用 Room 之后、下一轮调用开始之前，如果世界被别的行动改变，Room 重新预检的结果可能与工单不一致，这次修订会失败。
- 审计的已知缺口已清空，审计测试登记为 SPEC 0016 的验收门。
- 没有真实调用验证。模型很少在同一份稿子里犯两个独立的错误，真实批次只能确认没有退化。
