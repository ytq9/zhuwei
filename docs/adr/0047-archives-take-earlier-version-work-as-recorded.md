# ADR 0047：归档按记录接受早先版本的工作

- 状态：已接受
- 日期：2026-09-25
- 依据：[ADR 0046](0046-a-room-keeps-its-model-while-the-workflow-version-follows-the-deploy.md) 让房间跨版本继续后，归档校验仍用当前代码重建每次模型调用的请求，证明裁决出自那次回复。早先版本的调用无法这样重建。房间级测试里，一个在早先版本下提交过行动的房间连归档都导不出来（`archiveIntegrityMismatch`），恢复和历史分支也就无从谈起。[ADR 0038](0038-reask-unfinished-work-after-a-version-change.md) 已把这一点记为未覆盖。用户比较过“只核对记录本身”“登记历史版本号”“暂不处理”后选择第一种，并说明：“这只是个游戏，不会有安全问题，即使有人篡改历史文件也没问题，但要保证历史分枝和恢复房间等功能可以正常使用。”
- 当前规则：[SPEC 0011 §3](../specs/0011-reliability-correction-observability-and-evaluation.md)（已冻结的方案和已提交的结果保留当时的版本记录，归档导出和恢复按记录的版本核对，不按当前版本重新校验）
- 取代范围：ADR 0038 与 ADR 0046 各自的“未覆盖”一项；归档校验要求玩家行动、NPC 决定、旁白和故事 NPC 待办的每个阶段都记录当前版本 hash 的做法。

## 决定

1. 归档校验照旧核对每次调用的身份：账本里有这次调用，请求 hash 与记录一致，调用绑定与来源、调用键和用途一致。
2. 一份工作当前一轮的阶段都记录着当前版本的 hash 时，照旧用当前代码重建请求并做完整证明。只要有一个阶段记录的是其他 hash，这一轮就按记录接受：不重建请求，不解析回复，也不用当前代码重新推导它选中的故事准备。旁白按阶段判断，因为生成与审核阶段和修稿阶段各有自己的版本 hash。
3. 冻结输入仍按世界状态核对，不受版本影响：玩家行动的冻结上下文与投影、NPC 决定的冻结请求、旁白的可渲染事实、故事 NPC 待办的冻结请求。

## 后果

- 跨版本的房间可以导出归档、从归档恢复、建历史分支。
- 改写归档的人可以把某次调用标成其他版本，从而跳过该调用的完整证明。现有测试中“改掉版本标记必须被拒”的两条改为“按记录接受”。篡改冻结输入仍会被拒。
- 世界事件宿主的故事选择调用有自己的版本 hash，与 KP 指引无关，本决定未改动它。
