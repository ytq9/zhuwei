# ADR 0132：随身物品先列清单，点名后再读

- 状态：已接受
- 日期：2026-10-10
- 依据：本地复现玩家说"我把刚取出的这一块放回同一只敞口木桶。"时，冻结上下文没有行动者手上那块布条的实物记录。行动者自身记录里只有它的引用，库存表单因此没有这个来源，普通取放声明以 `frozen-visible-container-required` 拒绝，缺的其实是来源实物。说出"这一块布条"才能检索到它。用户在两种修法中选了"先匹配再加载"：不全量冻结随身物（带探险者套装的战士约 12 件，每次请求约多 4,600 估算 token），也不只补刚经手的物品。
- 当前规则：[SPEC 0016 §4.3](../specs/0016-coarse-forms-frozen-adjudication-context-and-typed-claims.md)（精确读取行动者持有物；条款不变）。
- 取代范围：冻结上下文只在行动者记录里带持有物引用、未被检索到的随身物没有实物记录的做法（2026-09-07 检查点 `72201ea` 引入，没有对应 ADR）。

## 决定

1. **冻结时列清单，不读正文。** 行动者随身、可以直接拿到、闭包没有读到的物品，各列一行：名称、数量、装备位或所在容器，以及点名时要读的记录（实物本身、它的定义、它带来的使用和武器能力）及各自的版本。除编号外完全相同的物品合成一行并记件数，点名时读第一件。装备中的和直接带在身上的排在前面，最多 24 行，其余只计数。关着的容器里的物品不列，行动者记得的是那个容器的查看记录（[ADR 0130](0130-container-inspection-and-original-content-provenance.md)）。
2. **发给模型的是精简清单。** 模型看到 `references.possessionRecall.requestable`：引用、名称、数量、件数和位置，以及未列出的件数；版本留在服务器。
3. **选择或补选点名后由 Room 读取。** 选择工具在有可点的随身物时多一个 `requestedItemRefs` 字段。点到的引用和记忆编号走同一个调取请求（[ADR 0051](0051-unread-memories-are-read-when-named.md)）：Room 从权威状态读出这些记录，核对版本和内容哈希，存进这次行动的准备数据，之后的各阶段、降级、阶段核对和归档恢复都读这一份。冻结之后记录变了，这次行动按调取失效失败，不会拿新值顶替。点到的物品已在表单里（随行动冻结，或之前的阶段读过）时按没选读，同 [ADR 0096](0096-a-requested-view-already-loaded-is-read-without-it.md) 对已加载 NPC 视图的处理；首个真实样本把放回动作的目标盒子写进了 `requestedItemRefs`，整个行动因此失败。既不在清单、也没有加载的引用仍然拒绝。
4. **各阶段只看到自己点过的。** Room 保存所有阶段读过的记录；某个阶段的视图只显示该阶段点过的物品，没点的仍以清单行出现。普通容器取放声明（[ADR 0131](0131-frozen-wire-references-and-declared-container-transfer.md)）的候选必须同时是该阶段库存表单列出的条目，因此补选时才读到的物品不会出现在更早阶段 Room 重建的请求里。
5. **缺来源时直说。** 声明里的物品这一阶段没有读到时，诊断为 `container-transfer:source-not-read`，并指出随身物要先在 `requestedItemRefs` 里选出，不再报成容器问题。

## 后果

- 本地测量（保守估算器，12 件不同随身物）：选择请求多 465 估算 token，可补选的填写请求多 469；点名某件物品时，填写阶段再加上它的记录和定义。服务器端冻结上下文另存这份清单（12 件约 7,400 字符）。随身物品完全相同时只占一行，行数上限 24，所以成本不随物品件数无限增长。
- 固定请求体积不变：没有可点的随身物时不出现该字段和清单。
- 解析器契约升为 v89，模型上下文升为 vnext-17；进行中的调用按现行换版规则处理。
- 模型仍可能不点名就填写；这时表单没有该物品，补选可以补点一次，和 NPC 视图召回相同。真实模型是否会主动点名，本地脚本测试不能证明，需要有限的真实样本验证。
