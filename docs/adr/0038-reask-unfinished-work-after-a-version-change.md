# ADR 0038：部署换版本后，未完成的模型工作重问一轮

- 状态：已接受
- 日期：2026-09-23
- 依据：用户于 2026-09-23 选择“换版本后重问一次”而不是保留旧版本提示；确认多花一次调用的费用可以接受，并同意“玩家已看到的裁决不在其不知情时替换”。
- 当前规则：[SPEC 0016 §9.2](../specs/0016-part-d-staging-and-supersede.md)
- 取代范围：为 SPEC 0016 §7.2、§9.1 与 SPEC 0015 §6.1、§8.2 中“恢复复用已保存的响应、不重新选择版本”增加一个例外，只适用于部署改变版本、且工作尚未冻结或提交的情况。其余恢复规则不变。

## 背景

每次模型调用都连同版本 hash（提示、schema、请求组装）保存，恢复时要求完全一致。部署一改提示，部署当时还没做完的工作就接不上：

| 未完成的工作 | 部署前的结果 |
| --- | --- |
| 玩家行动做到一半（方案未冻结） | `PROPOSAL_REPAIR_EXHAUSTED`，行动失败 |
| NPC 到期决定已保存未提交 | `dueActorPlanInvocationIntegrityMismatch`，到期工作一直待处理，房间之后的每个玩家行动都被拒 |
| 已提交行动的旁白未发布 | 调用身份冲突，恢复按钮反复失败 |

曾考虑的另一种做法是在代码里保留旧版本提示，让未完成的工作用旧版本做完。它不多花调用，但每次改提示都要登记和清理旧版本。用户选了重问。

## 决定

1. **何时算换版本**：以工作第一阶段为准，冻结输入（context hash）不变而绑定 hash 不同。NPC 决定和旁白的请求由 Room 自己重建或核对，所以重建出的请求不同也算。玩家提案的请求由调用方送来，只看绑定 hash：同一版本下送来不同的请求仍按冲突拒绝，否则伪造的请求就能让已保存的工作作废。
2. **哪些工作重问**：方案未冻结的玩家行动（没有确认、澄清、随机、执行或提交）、未冻结未提交的 NPC 到期决定、未发布的冻结旁白。已冻结的方案此后不需要模型调用，按冻结内容继续，所以“玩家已看到的裁决”不会被替换。
3. **怎么重问**：旧版本的全部阶段证明作为一轮移入 `authority_vnext_superseded_stage_proofs`，按当前版本从第一阶段重来。第 n 轮的调用键加后缀 `@rn`（原轮不带后缀），与旧轮的记账调用互不冲突；轮次由已移出的轮数推出，归档恢复后仍一致。
4. **额度**：新一轮的阶段次数重新计算。实际调用仍计入来源和房间预算（来源额度 24 次，一轮提案最多 6 次）。旧调用即使结果未知也不再等待，晚到的旧响应只作计费证据。
5. **归档**：宿主载荷新增可选字段 `supersededStages`（只在发生过重问时出现，其他载荷的 hash 不变），旧轮调用由它们持有；归档校验只核对旧轮的调用身份，不按当前版本校验其内容；恢复时写回审计表。

## 后果

- 门：`provider.room.test.ts` 覆盖提案重问、提案重问后的归档导出与恢复，以及已冻结的澄清不重问；`actor-plan-due.room.test.ts` 覆盖 NPC 决定重问以及之后的玩家行动不再被拒；`interrupted-publication.room.test.ts` 覆盖草稿已保存和调用结果未知两种情况下的旁白重写。原有的“同一版本下改请求被拒”测试继续通过。三条路径去掉修复后都复现了原失败。
- 改提示后可以直接部署。每份在途工作最多多花一轮调用。
- 未覆盖：归档恢复时会按当前版本校验*已完成*工作的旧阶段（`validatePrepared`、旁白与 NPC 宿主都要求绑定 hash 等于当前版本）。所以改过提示之后，从归档恢复一个有旧历史的房间仍可能失败。这是灾难恢复路径，与本决定无关，另行处理。
