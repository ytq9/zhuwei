# ADR 0078：回答审核的系统消息与填写调用开头相同

- 状态：已接受
- 日期：2026-10-01
- 依据：用户查看 2026-09-30 本地预览的 token 用量后，要求“修复审核未命中的情况”。
- 当前规则：[SPEC 0016 §7.2](../specs/0016-part-c-compound-actions-and-claims.md)（审核读取同一冻结主持人材料；系统说明与完整冻结上下文位于稳定前缀；条款不变）
- 取代范围：[ADR 0076](0076-review-npc-replies-and-admit-experiences-with-knowledge.md) 实施时审核请求的排列，即 `zhuwei.npc-reply-review/v6` 的 `frozen-context-first-changing-ticket-last-v1`：审核说明单独作系统消息，冻结上下文放在其后的用户消息里。

## 原因

2026-09-30 19:32–19:38 的本地预览里，两个与莉安交谈的行动共 16 次调用，输入 479,321 token。回答审核 5 次，占输入的 41%、未命中的 43%。每个行动的第一次审核几乎全部未命中：输入 34,840 与 42,118 token，命中 0 与 1,792。

原因在排列。审核的系统消息只有 841 字的审核说明，冻结上下文在其后的用户消息里；填写调用的系统消息以阅读说明和同一份上下文开头（[ADR 0043](0043-the-frozen-context-goes-in-the-system-message.md)）。两个请求从第一个字节起就不同，填写调用几秒前写入缓存的上下文，审核用不上。

审核的上下文也不是按填写调用的视图生成的，而是只按被交谈的 NPC 生成，不带选择阶段读取的记忆正文和点名的旁观者视图。19:32 的行动选择读取了莉安的两条记忆：裁决读到了；审核的主持人上下文把它们列为未读，只在莉安本人视图里出现。

## 决定

1. 审核请求按 ADR 0043 的排列发送。系统消息依次是：阅读说明；该行动填写调用发送的冻结上下文，由同一函数按同一组视图生成，字节相同；换行后是审核规则。工具在系统消息之后。被审的裁决、回答、候选和工单是最后一条消息，不再附带上下文。
2. 视图取填写调用实际加载的那一组：选择或唯一一次补选点名的旁观者视图和读取的记忆正文。Adapter 用本次填写所用的选择；Room 从保存的选择与补选响应推出同一组，重建请求后逐字比较。
3. 审核规则里的 `context` 改称 `requiredContext`，与上下文的键名一致。其余审核规则、表单、候选、阶段与重发规则不变。
4. 审核策略升为 `zhuwei.npc-reply-review/v7`。工作流 hash 随之变化，尚未冻结的方案按 SPEC 0016 §9.2 重问。

## 影响

- 用两个行动保存的数据离线重建，没有调用模型。新审核请求与当时实际发送的填写请求，系统消息开头分别有 62,105 和 73,357 个字符相同，正好是阅读说明加冻结上下文。被审材料与原审核请求一致，工具不变。请求分别多 2,548 和 1,249 个字符：阅读说明 1,250 个，19:32 的行动另加莉安的两条记忆正文。
- 估算：按原审核请求每字符约 0.40 token 计，第一次审核约可命中 2.5 万至 3 万 token，未命中从 3.5 万至 4 万降到约 1.1 万至 1.3 万。实际命中以真实调用返回的 `prompt_cache_hit_tokens` 为准，本次没有真实调用。
- 同一行动的后续审核与第一次的系统消息和工具相同，仍从第一次审核留下的前缀命中。
- 审核现在先读写给 KP 的阅读说明，再读审核规则。NPC 工作请求已按同一排列运行（ADR 0043）。审核结论是否因此变化，需要真实批次观察。
