# ADR 0070：审核打回时自己改稿，改好的正文再复审一次

- 状态：已接受
- 日期：2026-09-29
- 依据：用户提出“审核既然已经发现有不符合的事实，让审核把不符合的内容去掉再润色一下”，并在三种做法里选定“审核改完再复审”，同时确认修改 SPEC 0015 §7 和 SPEC 0016 §8.3。声口的用法来自用户同日的两步裁定：旁白可以描述 NPC 说话的语气；NPC 这次没有说到的内容不能写。
- 当前规则：[SPEC 0016 §8.3](../specs/0016-part-c-compound-actions-and-claims.md)、[SPEC 0015 §7](../specs/0015-part-b-proposal-and-narration.md)。
- 取代范围：取代 [ADR 0024](0024-narration-publication-and-bounded-repair.md) 和 [ADR 0026](0026-provisional-results-and-natural-narration.md) 中 plainText-v1 回复“由生成侧修稿一次、再独立复审”的做法。一次改稿、禁止无限重试、原调用恢复和回复先于世界提交的原则不变。旧策略 `narration-vnext` 已保存的四阶段流程不变。

## 原因

[round148](../agent/receipts/vnext-round148-validation.md) 的 148-1 里，审核的思维链已经写到“这一场她没有提到酒窖或歌”，结论仍是 `pass`。打回的代价是再调用两次，复审不过还会让整条回复失败，审核在“算不算严重到要打回”上倾向放行。

原流程里修稿由不带思考的生成调用完成，它只拿到问题理由；真正核对过冻结材料的是审核。148-3 的修稿只是删掉了被指出的那一句。

## 决定

审核判 `revise` 时，在同一份报告的 `body` 里给出改好的完整正文：删去或改正有问题的内容，其余保留，可以顺一下衔接，不添加冻结材料之外的内容。改好的正文再接受一次独立复审，通过才发布。

- 一条回复最多三次调用：生成、审核、复审。复审只审不改；复审仍判 `revise`、无法判断或报告损坏时回复失败，复审报告里的 `body` 不使用。
- `pass` 和 `uncertain` 的 `body` 必须为空。`revise` 的 `body` 不能为空，不能与被打回的正文相同，并受初稿同样的长度和格式约束。不满足时报告按损坏处理。
- 复审与审核使用同一份提示、同一份冻结材料，只有候选正文不同。
- 审核和生成共用的事实边界里加一句声口的用法。
- 旁白策略升为 `zhuwei.text-narration/v4`，审核协议升为 `zhuwei.narration-review/v15`。Room 判断一条回复能否继续时，先看已保存阶段的版本；早期版本保存的阶段不由新版本解读，重试时整条回复重问（SPEC 0016 §9.2）。

## 没有采用

- 只删句、不改字：审核返回句子编号，服务端删除后直接发布。不会引入新文字，但处理不了句子内部的错误，也不能润色。
- 审核改完直接发布：少一次调用，改好的正文没有第二次核对。

## 影响

- 打回路径由四次调用变为三次，少一次生成调用。
- 审核报告变长：打回时要写出完整正文，输出 token 增加，仍在 16,384 的上限内。
- 改稿由带思考的调用完成。它仍可能写错，所以保留复审。
- 提示词增加：声口一句进入生成和审核提示，改稿说明进入审核提示。
