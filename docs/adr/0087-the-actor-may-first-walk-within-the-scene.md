# ADR 0087：行动者可以先在本场景内走到某处，再做这一步

- 状态：已接受
- 日期：2026-10-03
- 依据：用户 2026-10-03 要求单独处理"行动者移动"：玩家的一次行动常先走过去再做事，例如"我走到楼梯阴影里，一把将奈斯拦腰抱起，扛到炉边的烛光下"。同日小测（`claude/kp-battle` 上的 `docs/agent/receipts/kp-refusal-form-mini-test-20261003.md`，样本"抱起奈斯"）里，填写表单有"做不到"时 KP 以"奈斯不在手边"拒绝，没有时写一次检定，成功也不改变任何人的位置。用户随后裁定：步骤上写"先走到谁旁边"；目的地可以是人、地图物件或坐标点；不做搬动别的生物；黑橡开场站位本次一起改，并确认 SPEC 0014 §§2.1、4 的条款文字。
- 当前规则：[SPEC 0014 §§2.1、4](../specs/0014-observer-tactical-map-and-environment.md)
- 取代范围：无。

## 原因

场景内的位置只有战术地图坐标（`combatRuntime.entities[id].position`）。遭遇之外坐标从不改变：换场景时落到新场景的出生点，遭遇中才有逐格移动。KP 的填写表单没有"先走到"的写法，Rules 也不移动行动者，所以 KP 只能拒绝，或写一个成功后谁都没动的检定。

黑橡的开场坐标是出生点排成的一行，NPC 按角色 id 排在玩家之后依次占位：一名玩家时奈斯在 (-60,-240)，离炉台很远，莉安也不在炉边，与开场描写不符，KP 读到的是坐标。

## 决定

1. **表单。** worldInteraction 与 observe 步骤加 `approach`：`{kind:"none"}`、`{kind:"nextTo", ref}`（场景里的人或地图物件）或 `{kind:"point", x, y}`（与 position 同一坐标系的英寸值，高度沿用行动者当前高度）。领域稿里不移动的步骤没有这个字段，与此前的草稿逐字节相同。交谈步骤不带 `approach`：交谈的 NPC 视图冻结时不允许行动者在这一步之前有变化，要先走近交谈对象就另写一个带 `approach` 的 worldInteraction 步骤；它写入行动者实体，按原有的快照依赖排在交谈之后执行。
2. **Rules。** `WorldInteractionResolutionPlan` 有可选的 `approach`。原子执行在每一步之前，用当前候选状态规划路线，提交新事件 `CharacterRepositioned`（行动者、场景、路径、走向哪里），再把这一步的读取集绑定到走后的状态，所以这一步的检定、攻击距离等都按走到之后的位置算；暂停后恢复时行动者已在终点，不再重复。路线：在场景的 30 英寸格点上找最短路，不穿过不可通行物（含隐藏的），可以穿过别的生物，终点不与他人占位重叠，不越出场景边界，不改变高度；终点可以是格点，也可以是紧贴目标一侧的位置，或坐标点本身。"旁边"指水平 5 尺内且高度范围有重叠，矮柜台旁站着的人也算。遭遇中、不能移动、目标不在本场景或看不见、走不到时拒绝。直接走 `resolveWorldInteraction` 的单步输入带 `approach` 一律拒绝，只有原子步骤会先走。
3. **降级与诊断。** 降级时用同一规划在冻结状态上先检查一次，问题定位到 `approach` 字段，`nextTo` 出错时列出可以站过去的引用，供 KP 修订。这个只读检查经 `rules/authority-read.ts` 提供，不新增对 `rules/v2` 的私有引用。Rules 执行时重新规划，KP 写的坐标或引用在执行前被改动也由 Rules 拒绝。
4. **事件的消费者。** 看得见场景的观察者得到 `mechanicalOutcome`（`walkedNextTo` 或 `walked`）；更正这次行动时恢复行动者的地图位置；地图和后续裁决直接读状态里的新坐标。
5. **不做的事。** 不搬动、推动或拖动别的生物（用户裁定）；扛人出门到别的场景还与 [SPEC 0006 §7](../specs/0006-module-npc-and-faction-protocol.md) 冲突。不支持爬高、改变高度。行动时长较长、以 Activity 执行时，走动在 Activity 完成时随这一步一起提交。
6. **黑橡开场站位。** 新登记模组版本 `social-resolution-v2`：wake 场景加"账台"和"通往楼上的木楼梯"两个地图物件，莉安在炉台旁 (360,0)，奈斯在楼梯旁 (270,270)，瓦罗在账台旁 (60,240)，玩家出生点移到西侧入口一带；其他场景不变。Rules 的开局角色种子接受可选的 `tacticalPosition`，有它的角色按它放置，其余角色依次占用未被占的出生点。新房间用 v2；房间保留创建时的版本，v1 继续登记、内容和哈希不变。开场准备目录按版本给出；前提目录按模组档案 id 生成（v1 不变）；房间绑定校验接受该模组任一已登记版本；历史房间沿用源房间的版本。KP 上下文展示地点锚点时去掉开场站位，人物现在站在哪里只看状态。
7. **指引 v71。** 加一句 `approach` 的写法。与 `claude/kp-battle` 上"做不到"填写说明里"原意图里的走近、移动等前置步骤不算缺少前提"重复的半句没有加。按 [ADR 0057](0057-request-size-may-grow-for-a-feature-the-user-was-told-about.md) 告知后接受请求体积：observe、worldInteraction 及含它们的三个组合的填写请求各多约 447–449 个估算 token，22 类全部加载多 758，选择阶段多约 108；字段在 steps 与 check 两处各出现一份，DeepSeek 严格模式不允许把联合类型提成共享定义。

## 影响

- 工作流 hash 变化，尚未冻结的方案按 [ADR 0038](0038-reask-unfinished-work-after-a-version-change.md) 重问。
- 已有房间仍按 v1 的开场坐标；只有新房间按开场描写站位。
- `claude/kp-battle`（ADR 0084、0085）和 `claude/contested-check`（ADR 0086）也把指引升到 v71，并改了同一组填写表单文件：后合入的一方顺延指引版本号，重新钉工作流 hash、按 ADR 0057 重新接受请求体积，并确认各自加的句子不重复。
- KP 是否会在合适的时候写 `approach`、是否不再因"不在手边"拒绝，本次没有真实模型调用验证。
