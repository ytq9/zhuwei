# ADR 0043：冻结上下文放进系统消息，排在工具之前

- 状态：已接受
- 日期：2026-09-24
- 依据：DeepSeek 的前缀缓存按系统消息、工具、其余消息的顺序匹配，遇到第一个不同的字节就停止。原排列把冻结上下文放在工具之后的用户消息里，而选择、填表、修订三步的工具各不相同，所以同一行动的后续调用从来没有命中上下文。[round121](../agent/receipts/vnext-round120-validation.md) 三次提案调用分别命中 2,560、1,792、18,048 个输入 token。用户批准：“把固定规则和冻结上下文放进各步都相同的系统消息，把各步不同的说明挪到工具之后。”
- 当前规则：[SPEC 0016 §7.2](../specs/0016-part-c-compound-actions-and-claims.md)（“系统说明、所选表单和完整冻结上下文位于稳定前缀，变化的草稿与诊断靠后”，条款不变）
- 取代范围：取代 2026-09-21 `832dae7`（指引 v31）的三条消息排列，即把与行动无关的规则放在最前、上下文单独一条消息的做法。

## 决定

1. 提案调用发送两条消息。系统消息依次是：读取冻结上下文的说明；冻结上下文，一行 JSON，紧接说明的最后一句；换行后是本阶段的规则。工具在系统消息之后。最后一条消息是本次调用要做的事。
2. 同一行动的选择和填表共享说明与上下文。修订调用重复填表的整条系统消息和填表表单，所以也命中填表规则。跨行动只共享说明。
3. 本阶段的规则放在上下文之后、工具之前，而不是放到工具之后：放在工具之后时，修订调用就命中不到填表规则。代价是选择调用不再跨行动命中选择规则（约 1.2 万字符）。同一行动内多命中的上下文比这部分大得多。
4. 三部分放在一条消息里要多一个换行。上下文紧接说明的最后一句，不另起一行，抵消了这个换行，按能力的请求体积与原基线相同（[ADR 0035](0035-ratchet-the-vnext-proposal-request-size.md)）。
5. Room 按同一排列核对保存的请求：拆开系统消息，规则逐字比较，上下文在故事存档的 canonical 呈现下按值比较。NPC 工作请求用同一排列。
6. 指引 v44，policy 增加 `requestLayout` 标记。工作流 hash 与 NPC 工作绑定 hash 随之变化，部署后未完成的工作按 [ADR 0038](0038-reask-unfinished-work-after-a-version-change.md) 重问。

## 后果

- 选择阶段按请求加载了 NPC 视图或记忆时，填表调用的上下文会在中间多出条目，缓存只能命中到第一个不同的位置。round121 的选择与填表上下文只有前 31,357 个字符相同，约为一半。
- 节省多少以真实批次的实际命中为准（SPEC 0016 §7.2 要求记录 Provider 实际缓存命中，未经测量不承诺节省比例）。
