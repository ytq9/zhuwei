# ADR 0058：房间模型调用的输入上限调到 90,000

- 状态：已接受
- 日期：2026-09-26
- 依据：用户问输入上限的作用、为什么是这个数、现在应改为多少。上限原为窗口 64,000 减输出预留 4,000 和余量 2,000，即估算 58,000；64,000 没有记录理由，随 `72201ea` 进入仓库，不是模型的能力上限。线上 9DCMQN 开局第 5 次行动的填写调用实际 46,485 token（估算约 50,200，已用 86%）；探针 round130 补选后的请求离线重建为 60,687，修订还要再加 4,000–5,000。建议窗口 96,000、允许 90,000，用户回答「可以」。
- 当前规则：`app/_runtime/lib/kp/vnext/runtime-policy.ts` 的 `VNEXT_PROVIDER_BUDGET`。上下文按相关性构造、超限如实失败不截断，仍按 [ADR 0015](0015-coarse-forms-frozen-context-and-typed-claims.md) 与 [SPEC 0016 §4.3](../specs/0016-coarse-forms-frozen-adjudication-context-and-typed-claims.md)。
- 取代范围：ADR 0015 中「独立完整 Provider 请求仍执行当前预算 Profile 的 58,000 估算输入额度（64,000 减 4,000 输出预留及 2,000 余量）」的数值。

## 决定

1. 提案、NPC 决策等房间模型调用的预算窗口从 64,000 调到 96,000，输出预留 4,000、余量 2,000 不变，允许估算输入 90,000。计数器每个汉字算 1 个 token，round104 对照时比 DeepSeek 实际计数高约 8%，所以约合实际 83,000。预算配置改为 `zhuwei.local-vnext-input-budget/v2`。
2. 上限仍是超限即如实失败的闸，不截断必要内容。请求超限时先查是否带了无关的表单或上下文，再考虑上限。
3. 故事准备路径的预算不变（允许 96,000）。

## 后果

- 此前被挡的较大组合可以通过，例如补选后 60,687 的请求及它的修订。上限只放行原本会失败的请求，不让正常请求变贵；一次接近 90,000 的调用，按空闲价、约一半命中缓存，约 ¥0.07。
- 工作流哈希包含预算哈希，部署后尚未完成的行动按 [ADR 0038](0038-reask-unfinished-work-after-a-version-change.md) 重新询问。
- `VNEXT_PROPOSAL_BUDGET`（窗口 32,000，允许 26,000）只是 `assembleProposalInvocation` 未传预算时的默认值，房间调用不经过它；任务书曾把它写成运行时上限，已改正。
