# ADR 0054：归档按 Room 持有的内容复制，不再重放核对

- 状态：已接受
- 日期：2026-09-25
- 依据：线上房间 9DCMQN（`room_22cb6874946c4b1d`）部署后开始游玩，第 4 次提交后归档核对每次用掉 26–32.5 秒 CPU，超过 Durable Object 的 30 秒上限；房间被重置，排在后面的玩家请求一起中断，玩家看到 500。定时任务随后从头重做同一页，15:10 起每约 35 秒重复一次，15:19 到 15:30 的 20 次全部超限。用这桌存入 D1 的归档（40 个事件、6 条动作记录）在本地实测：完整核对 16.0 秒 CPU，其中 83% 是核对每条动作记录时从创世重放到该事件；重放里最贵的是每一步对整个世界状态做规范化 JSON 和 SHA-256。核对成本随行动数约平方增长。用户裁定：「不要算哈希，这没用，都去掉」，并确认分三步去掉哈希，保留登录与会话哈希和日志脱敏，已有房间继续可读。本 ADR 是第一步。
- 当前规则：[SPEC 0011 §6、§10](../specs/0011-reliability-correction-observability-and-evaluation.md)
- 取代范围：归档页面按动作记录分页核对并留存核对记号的做法（2026-09-11 的[日志记录](../refactor-log/2026-09.md)）；[ADR 0047](0047-archives-take-earlier-version-work-as-recorded.md) 中归档仍逐条重建当前版本调用的部分；归档恢复比较代表性投影 hash 的做法。

## 决定

1. 归档页只复制 Room 持有的内容。头部取自 Room 自己的重放；导出时不再重放世界，不核对动作记录，不按收录回执重放，不生成投影审计。写 D1 前不再校验信封，写 checkpoint 前不再重放 D1 里的事件。
2. 读取归档（灾难恢复、故事档案、历史分支）只检查结构：字段、事件序号从 1 连续、同一房间和同一组 Profile。需要状态的读者重放一次得到状态，不与记录的头部比对。
3. 恢复按记录写回动作记录。仍在等待的 NPC 决定，按 Room 重放得到的最新状态筛选。恢复结果不再声称投影已核对。
4. 这一步不改归档格式：事件和信封里的哈希字段照旧写入，由后两步去掉。

## 后果

- 同一份归档：完整核对 16.0 秒降到 48 毫秒，组装信封 17 毫秒。
- 不再能发现：归档数据被改动或损坏、动作记录与世界不一致、恢复出的状态与原房间不同。
- 删除：动作记录核对和世界事件宿主核对（约 700 行）、Room 的核对记号表 `authority_archive_host_verification`（Room 启动时删除），以及只为这些核对存在的测试。
- D1 的投影审计表不再写入新行。已写入的旧行保留，不再读取。
