# ADR 0044：选择阶段加载的条目排在上下文最后

- 状态：已接受
- 日期：2026-09-24
- 依据：[ADR 0043](0043-the-frozen-context-goes-in-the-system-message.md) 让同一行动的选择与填表共享系统消息里的冻结上下文，但选择阶段按请求加载 NPC 视图或记忆后，填表的上下文会在中间多出条目：条目按 entryRef 排序，加载的记忆插在中间，列出未读记忆的 NPC 决策快照也随之改变。round121 选择读了莉安一条记忆，两份上下文只有前 31,357 个字符相同（共约 6 万字符），缓存在那里停止。用户批准的目标是让上下文进缓存（“改请求排列，让上下文进缓存”）。
- 当前规则：[SPEC 0016 §7.2](../specs/0016-part-c-compound-actions-and-claims.md)（条款不变）
- 取代范围：模型视图中条目按冻结顺序排列的做法（上下文表示 vnext-10）。其余不变。

## 决定

1. 模型视图先列不随选择请求变化的条目，再列随请求变化的条目，两组内部都保持冻结顺序。随请求变化的条目是：什么都不请求时会被隐藏或改写的条目，即在场 NPC 的决策视图、按 handle 读取的记忆正文、列出未读记忆的决策快照。
2. 这样填表的上下文与选择的上下文逐字相同，直到第一个随请求变化的条目；references 本来就在最后。
3. 条目内容和数量不变，Room 与 lowering 仍读完整冻结上下文，只有发送给模型的顺序变化。上下文表示改为 vnext-11，工作流 hash 随之变化，未完成的工作按 [ADR 0038](0038-reask-unfinished-work-after-a-version-change.md) 重问。

## 后果

- 上下文表示 vnext-9 起，一个身份或定义记录如果已有独立条目，就只列它的 ref。若某个随请求加载的条目正好被其他条目这样引用，那些条目在选择与填表之间写法不同，前缀会在第一个这样的条目处停止。测试夹具里加载 NPC 视图和记忆都没有出现这种情况。
- 模型看到的条目顺序变了：NPC 决策快照和本轮读取的记忆排在最后、references 之前。对裁决质量的影响要看真实批次。
