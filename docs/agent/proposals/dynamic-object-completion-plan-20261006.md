# 动态对象按需补全与使用链路

日期：2026-10-06。用户要求：此前剧情生成的新 NPC、物品、地形等，在首次需要尚缺的状态或机械属性时补齐，并验证使用前后的链路。门只是这项能力的一个样例。

状态：用户已批准 SPEC 0016 §7.2 的通用补全范围；四类补全、容器持久化与使用链路已实现。原批次证据及当时的桌面测试波动见[本地回执](../receipts/dynamic-object-completion-local-20261006.md)；后续按需表单、容器查看记录与四项 review 修复已完成本地实现，最新结果见[容器回执](../receipts/container-inspection-local-20261007.md)。现有沙盒接续任务继续保留，真实探针预算及剧本候选本人采纳的调用成本问题仍未获本轮答复。

## 当前优先级与范围

用户已明确：图形界面只是备选想法，本轮优先解决物品等对象的持久化与多次正确读取，不能在后续行动中反复新建同一个对象。新增对象面板和扩展地图不列入本轮必做范围；沿用现有文字、背包和地图入口。先完成状态连续性，再判断是否有必要增加界面。

身份稳定、已固化状态持续、重试不重复结算和叙述承诺不得被重写，已有 SPEC 0001 §§3.3、7、16 与 SPEC 0016 §§5.2–5.4 的依据，发现偏离时按 Bug 修复，不等待通用补全的条款裁定。用户已确认 NPC、库存实物、地形等进入 `completeObject` 的范围扩展。首次确定隐藏内容的时机继续服从 SPEC 0001 §7，不把“首次打开”当成唯一触发点；内容此前已提供因果证据时必须更早固定。

持久化纵切先验证“桶内已有三件实物 → 拿走一件 → 转交或使用 → 离开返回 → 房间恢复”。至少再覆盖另一类有持续资源的物品，以及两个同名对象、陈旧引用或重复提交中的最高风险边界。核对取回原身份、数量、容器/持有人归属、状态更新和玩家可见结果；无法解析引用不自动授权新建，同名也不自动视为同一对象。新建、补全缺项、执行操作和读取当前状态分别沿其现有职责验证。

现有实物记录、唯一物品绑定和叙述落实绑定已提供部分防重复机制，尚无证据表明每次行动都会新建。读取源码确认了容器关联的缺口：实物位置以场景或持有人表达，通用 `contains` 关系尚未与库存拿放自动同步。实施前先通过确定性用例复现具体断点，不能把仅有结构风险写成已经发生的实测错误。基础物品定向测试已在 `8b14eaaf` 快照通过 16 项，未覆盖真实模型的完整木桶往返。

## 能力合同

KP 对房间中已经存在的 NPC、实物、场景物件和地形，在当前交互需要尚未确定的语义或机械时，沿同一补全入口提出缺项，绑定原身份和精确版本，在首个受影响执行或随机之前由 Rules 验证、固化，并让原行动继续使用补全后的同一对象。已确定的事实、秘密权限、玩家意图和持续状态不因补全改变；重试和恢复复用已冻结内容。

依据：[SPEC 0001 §§3.3、7、8、16](../../specs/0001-llm-kp-responsibility-contract.md)、[SPEC 0016 §§5.1–5.4](../../specs/0016-part-b-sparse-semantics-and-primitives.md)、[SPEC 0015 §11.1](../../specs/0015-part-c-adoption-and-observability.md)。本能力不要求模拟完整现实物理，也不把物体名或动作词写成逐个脚本。

“首次使用”指第一次需要某组尚未定义的属性。例如 NPC 曾经交谈不代表其全部战斗属性已经用过；物件曾经被看见，也不代表其抗打击数据已经确定。后来的新用途可以再补此前无关的缺项，但已参与过结算的数据不能重新生成。

地点承载地图和连接。AC、HP、耐久属于其中适用的生物或可破坏物，不给每个地点或普通地面强行加一套生命值。地形按本次用途补齐通行、攀爬／游泳、掩护、危险或可破坏性所需定义。

## 已批准的规格修订

用户批准将 SPEC 0016 §7.2 原先“只补写已有的场景对象定义”的限制扩展，当前条款为：

> 补全已有对象（completeObject）用于 NPC、实物、场景物件和地形当前交互必需、尚未确定的语义或机械定义，不表示玩家已经操作对象。冻结上下文须包含获授权的原对象及精确版本，只有存在可补缺项时才提供相应填写面。补全保持对象身份、既有事实、秘密权限、伤势、数量、所有权、已耗资源和持续状态；明确不存在的能力不能借补全添加。服务端验证所有受影响的后续消费者，补全与原行动在首个受影响执行和随机之前冻结，沿同一权威事件及恢复链提交。

## 实现约束与直接影响

1. **一个公共补全入口，分别使用各领域原有事实源。** 共用缺项判定、版本和权限检查、冻结、顺序及失败合同；内部调用 NPC 定义、Item、Environment/Geometry 的原生编译和生命周期。对象名称、来自预写还是动态创作，都不选择专用脚本。
2. **区分尚未确定、已确定不存在和本次不适用。** 当前物品中的 null／空列表不能整体改解释为待填字段；新产生的未定部分须有明确表示。技术性加载失败也不能当成创作授权。创建时已要求并成功写入的完整数据直接复用，不为了“动态”再问一遍模型。
3. **补全不重置实例。** 原角色、实物和地图要素 ID 保持，绑定原定义及状态版本。仅合成完整下一定义和必要的原生绑定；同类其他实例、已消耗数量、充能、伤势、损坏、持有人和已识别知识不得被顺带改写。共享定义的影响须在提交前显式核验。
4. **先补全，再真实使用。** 普通组合动作、开战／能力调用和 NPC 自己的行动都检查本次必需数据。物品的新增原生能力、装备派生、实例计数器；环境的通行、掩护、视线和破坏后地形；NPC 的模板、装备与战斗状态必须一起满足消费者合同。不得另造一个同名对象绕过缺项。
5. **完整验证与原子失败。** 当前行动可达的分支在随机前检查。补全与后续操作有冲突、已定数据变化或仍不能执行时保持未提交并返回具体诊断；不吞错、不把技术缺口描述成世界中做不到。有效补全在检定成功／失败两条路径中保持同一内容，骰后不重定。
6. **补全本身不推进剧情时间或消费角色资源。** 玩家实际操作仍按其原耗时、检定和成本结算。默认复用本次选择／填写的调用流程；若最终方案需要新增调用或改变其他持续成本，另行给出具体影响，当前没有此项额外授权。

## 代表性验收矩阵

| 变化维度 | 从生成到首次使用 | 后续链路与拒绝边界 |
| --- | --- | --- |
| NPC | 新人物成立、交谈和知识保存后，首次战斗补齐仍缺的适用机械，再正常开战 | 先攻、攻击／伤害、战后记忆和下一次交谈；已伤 NPC 不能通过补全回满，不能覆盖既有属性或获得他人秘密 |
| 物品 | 新实物持有或放在场景中，首次使用前补齐明确未定的适用能力／耐久 | 使用的真实效果与扣量／充能／耐久、装备派生、转交后继续用、损坏／毁坏及知识保留；无重复实物或隐式复原 |
| 容器与重复读取 | 已确定的容器内容关联实际物品，拿出或放回按原对象结算 | 来源与去向同步更新，数量守恒；离开返回和恢复读取最新状态；同名不混淆，内容未知不等于为空，检索失败不触发重新生成 |
| 场景物件 | 无完整机械的门、普通可破坏物，以及已有状态图但缺耐久的对象，经同一补全合同处理 | 状态转换或破坏后实际改变通路、占位、视线和掩护；普通箱盖打开不自动撤销其空间占位 |
| 地形／地点 | 新地点经通路可达，首次需要攀爬、游泳或地形后果时补齐实际缺项 | 位置、地图、移动成本、检定与失败后果一致；离开返回仍是同一地点和定义，不为地面强加无关 HP |
| 冻结与并发 | 补全和原使用发生在同一实际输入的权威链中 | 已定事实、明确不存在、陈旧版本、未知目标、秘密受众及骰后修改均不能借补全绕过 |
| 持久化 | 本地 Room 入口贯穿填写、Rules 和观察者结果 | 同 submission 重试、DO 驱逐、归档恢复和可审计更正，不重复生成定义、重掷、扣费或改变身份 |

按 AGENTS 的三类直接证据验证：同一目标行为组覆盖上述变化维度；代表性路径走真实本地 Room 接口，模型回复可脚本控制但必须标明；公共类型变化后运行 typecheck。修改 SPEC 门后按 spec-workflow 实际运行声明的门。真实模型用例、浏览器体验和成本另按授权验证，不把本地绿色结果写成真实通过。

## 本轮交付边界

本轮代码已接通 NPC 战斗属性、实物的明确未定机械与开关状态、地图物件耐久及地形字段的原生补全，并加入容器关联和数量／位置连续性。补全仍由当前行动的表单与原子执行承接，不增加模型调用；新能力可先在同束登记，再由原物品调用并付费。当前完成的是本地实现与确定性验收，真实模型是否正确选择与填写仍待实测，不能据此宣称真实沙盒路线已经验证。图形界面、跨版本迁移和部署不在本轮范围。

原批次验证与请求体积记录在[原验收回执](../receipts/dynamic-object-completion-local-20261006.md)；后续补全表单精简见[表单回执](../receipts/completion-schema-routing-local-20261006.md)，容器产品决定和 review 修复的最新证据见[容器回执](../receipts/container-inspection-local-20261007.md)。
