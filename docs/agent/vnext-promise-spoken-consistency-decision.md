# 台词与承诺记录一致性：待裁定方案

2026-09-09。状态：**待用户确认，未接入运行时，未修改已批准 SPEC。** 本提案只针对新的 vNext。依据为已裁定生命周期合同 P01/P11、SPEC 0001 的正史写入边界及 SPEC 0016 §7.2 的冻结提案与调用额度。

## 需要决定什么

建议在含 social 的 Proposal 提交前增加一次只读的“台词—承诺记录”一致性检查。每份完整 social 提案至多多一次模型调用；不含 social 的动作不增加调用。即使 `consequences=[]` 也检查，否则无法发现本次真实遗漏。审查发现遗漏或矛盾时，整束保持未提交，返回可公开的技术错误；不自动增加承诺、不修改原台词、不生成新的行动或授予知识，也不追加语义重写调用。

它会增加对话的供应商费用与延迟，并需要在 SPEC 0016 §7.2 明确增加这一只读审核阶段及对应额度。现有每 HTTP 七次调用/120 秒上限保持，未实际发送的审核可在原请求恢复时续办；不能借此给每次对话增加无限修订。

## 已有证据与问题边界

独立批次 H 和 I 均经正常 Cookie HTTP、真实 DeepSeek、Rules/Room 和旁白发布。H 的 NPC 台词明确说写好会交到手上，I 的台词与私有动机也明确准诺写名签，但两份原稿的 `consequences=[]`。实际均无 `PromiseMade`、无 `NpcWorkProposed`，状态只是 8 个对话/时间事件；因此后台永远不会因为这次发言安排履行。

H 后已强化同源提示词，I 仍出现相同遗漏，说明仅补充该提示不足以证明问题解决。它不是普通拒绝或没有承诺的成功对话。现有 parser/Rules 能证明结构、引用、权限与实际状态，但不会凭中文关键词创造缺失的义务；也不能把 SourceClaim 的一句“会交付”直接当成已经履约。

证据包为 `/tmp/zhuwei-vnext-promise-live-20260909-h` 和 `...-i`；源码冻结、全部原响应、状态和精确 replay 均保留。审查方案尚未做真实模型对照，不能声称另一模型判断一定正确，或已证明可靠率。

## 可审查的实施边界

1. 插入点在最终 Proposal 已解析、引用和确定性预检通过之后，任何机械效果/Activity/随机/正史提交之前。它读取同一冻结原意图、双方身份，以及各 social 分支的原台词与对应承诺/改约条款；不重新读取世界或其他 Viewer 的秘密。
2. 一次审查覆盖该 Bundle 全部 social 分支，判断实际许诺、条件承诺、拒绝/追问/预测/转述与 `promise`、`promiseChange` 是否一致。原意图中的玩家新义务仍必须本人明确表达；检查者只判断是否一致，不成为义务作者。
3. 返回闭合 verdict 与准确分支路径、原台词片段。没有真实许诺的沉默或拒绝可通过；实际许诺却漏记、内容矛盾或不能可靠判断则拒绝本束。片段只留私有审计，公开返回仅有闭合原因类别，不暴露 NPC 动机或隐藏条款。
4. Room 在发送前保存精确请求、Proposal hash、schema/prompt binding 和只读材料；响应保存后恢复直接复用。响应未知不自动重发，预算未发与已发未知分开。审查失败不回写旧世界，不复用 H/I 的已提交对话来追补承诺。
5. 本提案不开放一次新的语义修订机会。已有窄 correction 不因审查意见升级为补造条款、改目标/成本/期限或重选原方案。若希望自动补齐遗漏，应另行说明语义冻结及调用变化再裁定。
6. 确认后同步 SPEC 0016 §7.2/直接规格引用、对应 ADR、阶段 DTO、持久 invocation、公共原因码及直接测试；不改动旧 V3、增加 D1 活跃表、部署或推送。
