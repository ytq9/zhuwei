# 9DCMQN 提示词与审核报告结构的对照

2026-09-29，用户要求只评审 [排查回执](kp-continuity-9dcmqn-20260929.md) 后提出的两处提示词修改方案，不改业务代码，并授权一次有界真实模型对照：上限 20 次物理调用、¥5，首个技术失败即停，同一请求不重采样。分支 `cloudflare`，HEAD `5e67695`。本次没有修改源码、提示词、规格、验收基线或房间数据，没有部署、migration 或 Git push。

## 被比较的文字

两段文字都是草稿，未写入仓库。

旁白审核（现役 [narration-text.ts](../../../app/_runtime/lib/kp/narration-text.ts) 的 `REVIEW`）。把“只报告实质问题……结果覆盖表。”一句换成：

> 先核对正文里每个人物：他做的动作、所在位置、持有的东西和说的话，要与冻结资料记在这个人名下的一致，不同人物的记录不能合到一个人身上。谈到某物或愿意出示某物，不等于正拿着它、在它旁边或已经做了那个动作。旁白自己断言玩家早已知道、刚才问过或双方谈过某事时，冻结资料里要有这段前情；首次透露、保留悬念和正常省略都合法。
> 只报告实质问题：结果改变或关键结果遗漏、与冻结事实冲突、人物的动作位置持有或说话者错配、没有依据的前情、未保存的新持久事实、来源或把握程度被加强、越权泄密、替玩家决定或认错观察者。以上不变时，自然同义表达、正常动作润色、短回应和个人文风偏好都应通过，不要求逐字引用、逐句举证或结果覆盖表。

NPC 回答（[proposal-guidance.ts](../../../app/_runtime/lib/kp/vnext/proposal-guidance.ts) 的 `social`）。在“玩家没有说过的话不能写进response.text、summary或relationshipChanges的依据。”之后加：

> NPC知道某事，不表示对方知道或双方谈过。对方听过什么只看actorSpeech和本人记忆里记下的交谈；没有这类记录的事，NPC可以这次主动说出或转开话题，但按第一次提起来说，不能当成对方问过或早已知道的旧话接着讲。

审核系统提示由 862 字增至 1049 字，实测每次审核输入多 116 tokens。`social` 多 108 字，实测每次填写输入多 62 tokens。

## 做法

- 模型 `deepseek-v4-flash`，参数与归档请求相同：thinking disabled、strict 工具、`tool_choice: required`、`parallel_tool_calls: false`，未指定 temperature。
- 审核请求用现役代码 `textNarrationReviewInput` 加 `kpRequestBody` 从归档的冻结旁白请求生成。R1、R6 使用归档原候选，生成的请求与归档物理请求逐字段相等。新提示只替换系统消息里的那一句，其余字节不变。
- 提案请求使用归档物理请求原文。新提示只在系统消息的锚点句后插入上面那句。这两份归档请求产生于 9 月 25 日至 26 日，使用当时的 guidance，不是现役 v66。
- 归档保存的请求按键名排序，工具 schema 的属性顺序是 `check, decision, steps`；生产发送的顺序是 `decision, check, steps`。本次提案请求按归档顺序发出，内容相同但属性顺序与生产不同，模型输出也按排序后的顺序填写。提案部分的结果因此不能当作生产请求的重放。审核请求由现役代码生成，属性顺序 `status, issues` 与生产一致。
- 首批 18 次调用里，两份旧提示的提案请求都返回了类型补选，没有可比较的台词。按“首个结果不能区分边界时追加一次对照”，用剩余 2 次额度追加 P1s：同一份症状请求，只保留提交工具，任务句换成同日归档的“只准提交”阶段原文。
- 每个（样例，提示）只发送一次。20 次调用全部返回 `finish_reason=tool_calls`，没有技术失败。

## 第二批：审核报告先写核对、后写结论

同日用户另行授权第二批：只测旁白审核，上限 10 次物理调用、¥1，其余纪律相同。实际 7 次，没有技术失败。

唯一变量是报告结构。审核提示文字保持旧版，只把“返回status为……”一句改为先填 `people` 再返回 `status`；工具 schema 的属性顺序由 `status, issues` 改为 `people, status, issues`，`people` 每项含 `name`、`inCandidate`、`inMaterial` 三个字符串。七份请求去掉这两处改动后与第一批旧提示请求的哈希相同。这个结构是草稿，现行 [SPEC 0015 §7](../../specs/0015-part-b-proposal-and-narration.md) 规定的报告结构是 `{status, issues}`。

| 样例 | 预期 | 旧结构旧提示 | 旧结构新提示 | 新结构旧提示 |
| --- | --- | --- | --- | --- |
| R1 原症状 | revise | pass | pass | revise |
| R2 正确改述 | pass | pass | pass | revise |
| R3 说话者错配 | revise | revise | revise | revise |
| R4 愿意出示写成已出示 | revise | revise | revise | revise |
| R5 旁白断言玩家早已知道 | revise | revise | revise | pass |
| R6 合法首次透露 | pass | pass | pass | pass |
| R7 说法写成事实 | revise | pass | revise | pass |
| 符合预期 | | 5/7 | 6/7 | 4/7 |

- R1 被拦住，理由准确：把盖印文件按在账台上的是瓦罗，奈斯只把遗嘱称作“这卷纸”；两者是否同一份文件资料没有证实。
- R2 被误拦。理由是正文读起来像玩家先提出“这卷纸”；候选原文写的是“奈斯方才说的‘这卷纸’”，这个理由不成立。
- R5 漏检。核对栏里已经写出“资料中未记录玩家此前已知道第三份遗嘱”，结论仍是 `pass`。
- R7 漏检。核对栏把旁白自己的断言“这家里确实还留着第三份遗嘱”记成了莉安说的话。
- 每次审核输出 286 至 834 tokens（旧结构通过时 52 tokens），单次耗时 1.6 至 4.3 秒。
- 三种做法没有一种在七个样例上全部符合预期。每格只有一次调用，R5、R7 的翻转可能是模型波动。

## 第三批：审核打开 thinking

同日用户授权第三批：R1 至 R7 各一次，共 7 次调用。实际 7 次，没有技术失败。

审核提示文字、报告结构 `{status, issues}`、冻结材料和模型不变。请求由现役 `kpRequestBody` 生成，只改四个参数：`thinking` 由 disabled 改为 enabled，加 `reasoning_effort: low`，`tool_choice` 由 required 改为 auto，`max_tokens` 由 2,048 改为 8,192。[官方文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion) 写明思考模式下不支持 `required`，会返回 400。去掉这四个参数后，七份请求与第一批旧提示请求逐字段相等。

| 样例 | 预期 | 关闭 thinking | 打开 thinking | 思考 tokens | 输出 tokens | 耗时 |
| --- | --- | --- | --- | ---: | ---: | ---: |
| R1 原症状 | revise | pass | revise | 1,850 | 2,101 | 9.8 秒 |
| R2 正确改述 | pass | pass | pass | 991 | 1,049 | 5.0 秒 |
| R3 说话者错配 | revise | revise | revise | 913 | 1,231 | 6.4 秒 |
| R4 愿意出示写成已出示 | revise | revise | revise | 1,270 | 1,585 | 8.0 秒 |
| R5 旁白断言玩家早已知道 | revise | revise | revise | 1,452 | 1,732 | 8.6 秒 |
| R6 归档原候选 | pass | pass | revise | 7,405 | 7,562 | 38.1 秒 |
| R7 说法写成事实 | revise | pass | revise | 1,075 | 1,292 | 6.9 秒 |

- 七次都以 `finish_reason=tool_calls` 返回一次 `review_frozen_narration` 调用，正文为空，现役解码可以直接使用。`tool_choice: auto` 下没有出现只回文字不调工具的情况。
- R1 被拦住。理由有两条：把盖印文件按在账台上的是瓦罗；奈斯原话的条件是“若您信这些风言”，正文改成了“不肯看”。两条都与冻结材料相符。
- R6 判 `revise`，与预期不符。理由是莉安原话“你凑近点，让我看清那些刻痕”是让玩家凑近，正文写成“莉安凑近看清了刻痕”。这个理由与冻结材料相符，R6 的预期标签来自当时线上审核放行，不能据此认定是误拦；它是否算实质问题取决于标准。
- R6 的思考用了 7,405 tokens，输出合计 7,562，距上限 8,192 只差 630。其余六次思考在 913 至 1,850 之间。
- 打开 thinking 后每个 `revise` 给出 1 至 4 条理由，其中有偏细的，例如 R7 指出正文把“第三份”写成“第三份遗嘱”。
- 本批没有测量正常旁白被判 `revise` 的比例；两个正例里有一个被判 `revise`。

## 对原诊断的一处补充

归档调用 `6308b782` 的冻结上下文里没有任何关于“信”的记录。莉安已加载的知识只有铜钥、门外的声音和“父亲说过还留有第三份遗嘱”。她主动说出“第三份”有知识依据；“信这事我确实记不清了”没有依据，是提案模型自己引入的话题。当时的系统消息已含“不能假定、转述或代替玩家尚未说出的回答”。
