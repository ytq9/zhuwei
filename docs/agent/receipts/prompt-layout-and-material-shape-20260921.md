1. `4348271` 旁白审核不再把同一批 policy 文本发两遍。

2 和 3 都动了 `VNEXT_KP_WORKFLOW_HASH`（→ `sha256:412199ba`），用户于 2026-09-21 明确授权移动该钉子。本地全绿不算工作，按 2026-09-05 的[有界授权](../vnext-production-todo.md#用户已确认的执行边界2026-09-05)跑一次真实链路。

## 重排收益的实测（同日补测）

首批的 97.5% 命中率不可用：那是同一批次参数的第二次运行，第一次已把完全相同的请求喂进缓存。随后在旧布局的 worktree（`4348271`）上重跑，两边得到**逐 token 相同**的 49,001/48,768/233 与 49,006/48,768/238——旧布局的 requestHash `05c021cd…` 与 round104 完全一致，证明 **DeepSeek 的前缀缓存至少保留 24 小时**，等过期不可行。

改用**新上下文**测量：给 `item` 用例的 prompt 追加一行唯一标记，使上下文成为 provider 未见过的内容，静态规则与 schema 保持热态。两个布局各一次调用：

| | 新布局（本轮） | 旧布局（`4348271`） |
| --- | --- | --- |
| prompt_tokens | 49,026 | 49,026 |
| prompt_cache_hit_tokens | **42,880** | **1,024** |
| prompt_cache_miss_tokens | **6,146（12.5%）** | **48,002（97.9%）** |
| requestHash | `sha256:de890b13…` | `sha256:a5b06573…` |

总量逐 token 相同——同样的文字，只是顺序不同。**每次新行动有 41,856 token 从全价转入缓存，提案调用的计费输入降约 87%。**

两次都以 `PROBE_PROVIDER_CALL_BUDGET_EXCEEDED` 结束：测量只给 1 次调用预算，而用例想用修订。invocation 0 的用量不受影响，那正是本测量所需。

### 顺带确定的一件事：system message 排在 tool schema 之前

旧布局只命中 1,024 token，约等于那段读取指引本身。若 tool 定义排在消息之前，旧布局应当命中约 33,000（schema）＋1,000。两边观测同时成立的唯一解释是序列化顺序为 **system message → tool definitions → 其余消息**：

- 旧布局把每次都变的上下文拼进 system message，于是它之后的 109KB schema 与 27KB 指令块全部失效。
- 新布局的 system message 是纯静态的，schema 因此始终命中，只有自己的上下文和 114B 的任务未命中。

这条对后续任何提示词布局改动都成立：**放进 system message 的可变内容，代价是它之后的整个 tool schema。**

### 这次补测的一个失败

旧布局的四调用批次在 hazard 例失败：`PROBE_LOWERING_REJECTED`，诊断 `PROPOSAL_REFERENCE_INVALID / world-interaction:registered-hazard-unavailable`，`repairUsed: false`、`invocationCount: 1`。这发生在改动前的代码路径上，round104 同一例是通过的，属于模型采样波动，不是本轮改动造成。按规矩保留，不重采样。


## 旁白改动的真实对照（同日补测）

probe 不经过旁白阶段，所以另做一次单变量对照：**同一份冻结材料**narrate 两次，一次用本轮的门控提示词，一次用改动前的完整提示词。完整提示词不是手工复原的——它就是「材料含全部 subject 时」产生的提示词，与原文逐字节相同。所有正文由**同一个审核**判定（该材料自己的审核），judge 不参与对照。

### 用例一：纯物品转交（六门全关）

| | 完整提示词 | 门控提示词 |
| --- | --- | --- |
| system prompt | 11,678B | 7,404B |
| 实测 prompt tokens | 3,189 | **2,308（−27.6%）** |
| 样本 | 2 | 2 |

四份正文：`远行者把两件玻璃镜交给了药师。`×3，`远行者把2件玻璃镜交给了药师。`×1（出自门控侧，中文数字换成阿拉伯数字）。五个维度全部 pass。

### 用例二：只有机械结果的观察（`perception` 关闭）

这是风险最高的配置。`KNOWLEDGE_EXPRESSION_GUIDANCE` 的门是「材料里有无感知/推断类 claim」，而这块里有一条**反编造**规则：「不得在已有结果之外追加死因、动机或谜底分析」。一次只含 `mechanicalOutcome` 的观察会让它被丢掉，材料又恰是最引人脑补的那种（门框下缘的新刮痕）。

| | 完整提示词 | 门控提示词 |
| --- | --- | --- |
| system prompt | 11,678B | 8,948B |
| 实测 prompt tokens | 3,174 | **2,612（−17.7%）** |
| 样本 | 3 | 3 |

六份正文的差别只有「木屑」那半句的动词（刮出来的／刮下的／蹭下来的／刮下来的），两个变体都有这种波动。**没有一份追加死因、动机、撬痕推测或把握度措辞。**五个维度全部 pass。

### 这组对照的边界

- **审核没有提供判别力**。十份正文全部 pass，审核一次都没有 fail，所以「两个变体等价」主要来自逐句比对，不是来自 judge 把它们区分开。
- 每变体 2–3 个样本，不构成成功率。
- 未覆盖复杂材料（多个机械组、社交承诺、知识回顾）。不过那些材料会保留对应规则，风险低于本组测到的配置。

### 顺带：保守计数器在旁白形状上高估约 36–40%

先前本文件记的 4,474 / 3,138 是 `conservativeInputTokens` 的估算；实测是 3,189 / 2,308，比值 1.40 / 1.36。[ADR 0035](../../adr/0035-ratchet-the-vnext-proposal-request-size.md) 在提案形状上实测的余量是 1.08，并写明「不能外推到旁白或审核」——本组证实了这一点，方向仍是高估。

## 这一批不能证明的

- **生产形状的请求**。probe 不做能力选择，直接发全 16 能力，约 49,000 prompt tokens；生产 `VNEXT_PROPOSAL_BUDGET` 只允许 26,000，`assemble.ts` 会挡下这个形状。
- **准确度的收益方向**。上面的对照证明门控没有让正文变差，但没有证明它让正文变好：审核在两个变体上都零 fail，所以「去掉无关约束能减少审核误判」仍无证据。提案阶段的准确度也未设对照。

## 结论

真实模型路径在三消息布局与逐段装配的提示词下仍然贯通，请求体积与改动前逐 token 相同。本批未部署、未 push、未做远端 migration、未改 Secrets。
