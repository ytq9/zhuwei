## 缺陷与修复

1. 语义场景容器失败属实。最窄 Parser 用例在原展开器上返回 `container-transfer:mechanism-not-defined`。现在 Rules 与展开器共用只读的 `authoritySceneContainerState`，按地图状态、`content.observableState`、旧 `content.semantics.observableState` 的顺序读取。地图的 locked 不能被语义 open 覆盖，缺机制、锁定及他人持有的拒绝保留。Rules 原有行为没有改动，Parser 更新为 v87，未冻结请求按现役换版合同处理。
2. 实际 Room 用例动态创建敞口语义木桶和三块布条，取出一块，再放回原桶。两次取放均只加载库存表单，取出后的拆分实例放回仍保留原身份；总量恢复三、原桶定义不变、事件重放一致。该用例明确提到已建立的物品和容器名称；未声称没有对象名称的模糊回指都能自动加载其引用。调试中一次这种表述缺少冻结来源，改为明确命名后原通用路径通过，没有放宽引用授权。
3. 普通查看验收只允许针对所查容器里的、原定义已经 `visibility:public` 的实物执行 `identify`。隐藏定义反例由绿转红，再修复通过；真实布条的公开定义正例继续通过。没有因此修改生产鉴定能力或把普通查看等同于获取秘密。
4. 删除通用库存填写说明中与具体 `containerTransfer` schema 描述重复的 107 左右固定 token；实际提供的声明仍有字段枚举、取放方向与禁止隐式解锁/损坏/创作的说明。无冻结来源时请求不带该声明及其文字。指导更新为 v105；原生开盖、拿取、合盖路径保留，声明是可选填写捷径。

依据 SPEC 0001 §§12、16 与 SPEC 0016 §§4.3、7.1、7.3。未修改已裁定产品条款、事件、持久化结构或生产调用额度。
