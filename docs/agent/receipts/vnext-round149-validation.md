## 这批验证什么

[ADR 0070](../../adr/0070-a-refusing-review-writes-the-corrected-body-which-is-reviewed-once.md)：plainText-v1 审核判 `revise` 时在报告的 `body` 里给出改好的完整正文，改好的正文再复审一次，一条回复最多三次调用；生成和审核的事实边界里加了声口的用法。策略 `zhuwei.text-narration/v4`。

分两部分。第一部分直接向 Provider 发送审核请求，候选正文是已知有问题的真实旁白，请求由工作区的现役代码生成。第二部分用 `tools/run-story-room-probe.mjs --live` 走真实 HTTP 路径，每次一个新房间。

- V1 的理由与用户的裁定一致：声口里列出的话题这次台词没有说到，不该写；语气可以保留。改稿只动了那一句，其余逐字保留。
- V2 是漏检。同一份初稿在 round148-3 里被打回，这次通过。审核的思维链考虑过这句话，认为行动者的意图里有“趁莉安不注意”，没有当成问题。两次用的提示版本不同，各只有一次调用，不能判断是提示变化还是模型波动。
- V3 在现役流程里会以回复失败结束。第一次审核只指出了动作主体和“遗嘱”的来源，改稿保留了“不肯看，那就没什么可谈的了”；复审指出奈斯原话的条件是“若您信这些风言”，判 `revise`。复审的理由与冻结材料相符。按 SPEC 0016 §8.3，复审不再改稿，这条回复失败，行动不提交。

## 结论

- 新的报告结构和三阶段流程能通过现役校验、Room 的冻结请求核对和 strict 端点；`pass` 路径在真实 HTTP 入口上正常提交和发布。
- 审核能按声口的规则打回并改好 V1 这类问题，改稿保留语气、去掉没说到的话题。
- 改稿只修第一次审核列出的问题。第一次审核漏列的问题留在改稿里，由复审发现时，这条回复失败。V3 属于这种情况。
- 审核的判断仍不稳定：V2 这次被放行。
