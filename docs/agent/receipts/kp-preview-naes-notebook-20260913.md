## 原始证据与根因

实际房间为 `D9D3BG`，本地 Room ID 为 `room_d8518c52fb2f45e6`。

- Capture 158 的 NPC `response.text` 已包含“你们比他留下的那几张纸更想弄清事情”。Capture 161 的旁白沿用了病句，162 的审查全部通过。“不用你们付酬”来自同一提案中承诺的内部 condition，而非 NPC 原本说出的台词。创作、转述和审查均未把自然中文要求落实；“忠实原话”还被误解为照录错误句法。
- 06:51:48.448Z 的 `PROPOSAL_FORM_INVALID` 用时 1992ms。Capture 155 是唯一一次选表响应：奈斯已在默认加载名单中，模型仍把他放入 `requestedNpcRefs`；该字段当时只允许另外两名 NPC。原响应在真实保存的 RequiredContext 上重放，确定得到 `offer:requested-npc-ref-not-requestable`，路径为 `requestedNpcRefs[0]`。尚未生成 Proposal，不存在进入修订后丢失机会的情况。SPEC 0016 §7.2 的提案修订额度没有扩展到选表，也没有修改次数。
- 桌面适配器把非日常对话的知识记录逐条变为卡片。叶子的视觉、触感、推断成为三张卡；开场身份介绍等也占卡片。UI 还把完整持有层级 `full` 误称“已确认”，并错误声称全桌共享。

## 修改

- [中文表达规则](../../../app/_runtime/lib/kp/chinese-expression.ts) 同时供 NPC 创作、旁白和审查使用：日常口语、指代清楚、比较关系成立，修正句法但保留信息含义、来源、条件与不确定性。已定的口语要求和审查者个人文风偏好分开。
- [旁白](../../../app/_runtime/lib/kp/narration-vnext.ts) 在引用材料后再次说明写作任务，并将该指令纳入 Prompt hash。审查分别处理语言问题与真实语义改变，不能因“给钱／付钱”等正常同义表达而虚构玩家义务变化。Policy 更新到 v16。
- Proposal guidance 更新到 v30；选表末尾与字段描述明确：`requestedNpcRefs` 是补充加载名单，已经显示的人不重复选择，只有已加载对话对象时填空数组。NPC 承诺只记录本次实际表达的义务，不添加未谈及的收费条件。非法选表仍严格失败，不吞掉错误引用或增加调用额度。
- [线索整理](../../../app/_runtime/lib/table/knowledge-notebook.ts) 只消费当前 Viewer 的投影，以已公开对象身份和已有证据链归组；跨对象、不同来源及知识性质保持区别。同一对象一张卡，具体记录可展开；没有确定对象或标题的见闻折叠。没有改动权威知识或事件。UI 去掉“全桌共享／已确认／继续检定即可升级”等错误说明。
- 格式错误提示不再让玩家因为模型格式故障而改变角色做法。
