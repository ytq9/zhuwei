# round153：NPC 本人作答的四个用例

2026-09-29。`tools/run-story-room-probe.mjs --live`，每次运行一个新房间，真实 HTTP 路径，`deepseek-v4-flash`。用户授权上限 40 次物理调用、¥5，四个用例各一个新房间，首个技术失败即停，不重采样，不部署、不 push。实际 21 次调用，按高峰标价 ¥0.789。第四个用例以技术失败结束，批次在那里停止，之后没有再发起真实调用。在主工作区运行，HEAD `3ea625e`；另一个会话未提交的 OpenAI 提供方改动不在 DeepSeek 路径上。没有远端 migration、Secrets 修改或部署。

## 这批验证什么

[ADR 0073](../../adr/0073-an-npc-writes-its-own-reply-from-its-own-view.md) 和 [ADR 0074](../../adr/0074-the-explicit-recovery-covers-the-npcs-reply-call.md) 的实现在真实 HTTP 路径上的表现：裁决不写 NPC 的回答，每名被交谈的 NPC 由一次只读本人视图的调用作答。提案指引 `zhuwei.proposal-guidance/v67`，解析合同 `kp-vnext2-proposal-parser-v76`，作答策略 `zhuwei.npc-reply/v1`。

运行前做了一次 `--preflight`，0 次模型调用，通过。玩家原话用 `--action` 传入；153-4 用的是 `daily-hidden-act` 登记的原文和断言。

## 各用例看到的

**153-1。** [round152](vnext-round152-validation.md) 第三问用的是同一句话，那次莉安的台词指向了神龛。这次发布的旁白是：“她回答：‘第三份遗嘱在哪里我不知道。父亲只跟我说过他另外留了一份，我连原件都没见过，更谈不上知道放在哪儿。’接着她又说，你要接着问别的，先报名字和来意。”没有发布的成功回答说的也是不知道。两份回答引用的都是她本人关于遗嘱的两条记录和她的身份记录。裁决自己的风险说明里仍写着藏处，那是主持人材料，没有传给作答调用。

**153-2。** 这一问的答案在莉安自己的记录里。检定失败，发布的回答没有交出任何一条记录：她说名字记下了，但不知道该信谁，今晚先听镇公所的，有事等弄清对方是谁带来的再说。没有发布的成功回答讲了她自己的三条记录，并留下铜钥的事没有说。失败时说到哪一层是她本人按“这番话没有起作用”决定的，这一次的结果是一条也不说。选择阶段按 handle 读取了她目录里的一条记忆，这条记忆进了她的视图。

**153-3。** 用的是 `daily-npc-leaves` 的第一句，只跑一步。莉安没有答应：她让对方先别支使她上楼，反问为什么一开口就要私下问酒窖和父亲的事。承诺表是空的，NPC 本人登记承诺这条路径在真实调用里没有走到。同一句话在 [round140、141](vnext-round138-validation.md) 跑过三次，当时台词由裁决调用写：两次她口头答应上楼，一次她不肯去客房、改约在后院。

**153-4。** 失败原因在裁决，不在作答调用。

- 裁决的结构是对的：隐蔽检定（巧手）挂在 worldInteraction 上，取叶是绑定 onSuccess 的库存操作，问话是绑定 always 的 social。
- 裁决在检定步骤的成功分支里多写了一条 `relationTransition`，`relationRef` 填的是黑橡叶的物品条目。物品条目不是关系定义，lowering 拒绝，诊断定位到 `branches.success.effects[0].relationRef`，标明允许修订，错误码是 `DEFINITION_CONFLICT`。
- 行动循环只对 `PROPOSAL_REFERENCE_INVALID` 发起修订（`app/_runtime/lib/room/action.ts`），这条拒绝直接返回给玩家，三轮修订一轮没用。遥测里的 `failureReason` 是 `unclassified`。
- 这不是 ADR 0073、0074 引入的：`action.ts` 和 effect 的 lowering 在这两次提交里没有改动。`5eca1dd`（2026-09-28）给 lowering 的拒绝加了字段定位，其中错误码不是 `PROPOSAL_REFERENCE_INVALID` 的几类（时长档位、合成被拒、补全的基底、隐蔽检定挂在与主要察觉者的对话上、effect 的关系或定义）此前都进不了修订。

## 批后的修复

`7dd0b90`：行动循环对“每条诊断都标明允许修订”的 lowering 拒绝发起修订，不再只看错误码；没有诊断、诊断标明不可修订或没有写明的拒绝仍直接返回。Room 证明修订资格时本来就用自己对已保存方案的 lowering 结果，不看错误码。

本地证据：

- Room 测试用真实模组重现了这次失败（一个带同样 effect 的动作加一句对莉安的问话）。修复前结果是 `rejected DEFINITION_CONFLICT`，诊断与 153-4 相同；修复后修订一轮，行动提交，莉安没有被再问一次，因为她听到和看到的内容没有变。
- 行动处理器测试覆盖三种错误码会修订、四种拒绝不修订，以及修订轮数用尽后以 `PROPOSAL_REPAIR_EXHAUSTED` 结束。
- `npm run typecheck` 通过；`tests/kp/npc`、`provider.room`、`stage3.room` 共 149 项 Room 测试通过；`authoritative-action`、`private-lowering-diagnostics`、`concealed-check`、`atomic-input` 共 88 项 node 测试通过。

修复后没有发起真实调用。真实模型拿到这条诊断后能不能改对、153-4 的方案其余部分能不能通过 Rules，本批没有证据。

## 结论

- 同一句问话，莉安不再说出神龛。作答调用读不到主持人材料，这一点在四份真实请求里都成立。
- 带检定的交谈在真实调用里两次都写出了成功和失败两份回答，Rules 按骰子取其中一份，旁白发布的与取用的一致。
- 检定失败时，153-2 的回答没有透露她的记录。“裁决为每个分支圈定 NPC 可说的记录”这一项本批没有显示出需要。
- NPC 本人登记承诺、隐蔽动作加问话的完整流程，本批没有验证到。

## 观察到、没有处理的

1. 153-2 的旁白结尾是结算式的句子：“交涉到此为止，没有欠下人情，也没有许下承诺。”旁白输入里 `socialRecords` 的 `newDebts`、`newPromises` 是空数组，必述事实里没有这一条。
2. 153-2 的旁白用名字和“他”称呼行动者，当时 `isActorViewer` 为真；153-1、153-3 用的是“你”。
3. 关系变化现在由 NPC 本人填写，仍是必述事实。153-2、153-3 的旁白把它写成了莉安心里的归类和戒备。
4. 153-1 裁决写给莉安的察觉内容里用“玩家”称呼行动者。
5. 153-4 裁决的 decision 文字里把赫斯写成了奈斯（察觉证据、风险、成败说明），步骤的 intent、method 里是赫斯。
6. 153-4 莉安的回答对“父亲是否常来”给了一个说法，她的记录里没有这件事的依据。该回答没有发布。
7. 153-2 玩家说了“我不往外传”，裁决的两个分支都没有登记行动者的承诺。
8. 153-1、153-3 的填写轮先调用了一次选择工具且没有新增，按 [ADR 0065](../../adr/0065-a-selection-repeated-without-addition-refills-the-form-instead-of-ending-the-action.md) 再发一次表单，各多一次调用。153-4 补选了两个类型，填写时都没有用上。

## 没有覆盖的

- NPC 本人登记承诺、改约、债务。
- 隐蔽检定的掷骰、察觉后的当场反应、取叶的库存结果和对应旁白。
- 作答调用的重问、结果未知后的显式恢复（ADR 0074）、部署换版本后的重问：都只有本地 Room 测试。
- 多人房间、同一行动里与两名 NPC 交谈、澄清的 continuation 共用回答。
