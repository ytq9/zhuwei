# 剧本写作与开场准备指导

适用于创建、补充剧本以及调整关键物品、开场知识和相关验收。产品行为服从 [SPEC 0001](../specs/0001-llm-kp-responsibility-contract.md)，模组与 NPC 边界见 [SPEC 0006](../specs/0006-module-npc-and-faction-protocol.md)。本文说明如何把这些要求落实为作者材料与当前输入，不新增产品规则。

当前可运行范例是 [黑橡开场补充](black-oak-opening-preparation.md) 及其 [准备 JSON](../../app/_runtime/lib/module/black-oak-will-preparation.json)。字段与校验以 [preparation.ts](../../app/_runtime/lib/module/preparation.ts)、[物品类型](../../app/_runtime/lib/rules/v2/items.ts) 和 [ModuleBible](../../app/_runtime/lib/module/authoritative.ts) 为准。

`module/writing.ts` 的修订 9 仍被旧格式及部分既有 Prompt 消费，不是新创作的上位合同。其中行动白名单、预写 NPC 计划限制、带 DC 线索必骰和固定两轮推进等要求，遇到冲突时以 SPEC 0001 为准。更新本指导不等于已经修订这些运行时 Prompt，也不需要为文档改动重命名 `WRITING_REVISION`。

## 1. 先确定故事事实和开放范围

先整理故事圣经，再填写开场准备；两份材料必须描述同一个世界。

| 作者材料 | 完成条件 |
| --- | --- |
| 核心真相与历史 | 人物年龄、事件先后、距今年数、死亡与继承关系、封印期限能够同时成立；来源主张中的谎话与作者事实分开 |
| 地点与起始局面 | 标清开场地点、人物位置、通行条件、可感知现象、现场冲突及已有危险 |
| NPC 与势力 | 写明目标、顾虑、有限知识、资源、关系、能力、声口和无人干预时的下一步；计划依据可追溯 |
| 线索与结论 | 关键结论有不同来源的证据；区分可直接观察的内容、需要解释的细节和未经核验的主张 |
| 开放留白 | 标清哪些内容尚未确定，以及创作须服从的历史、环境和势力条件；允许合理的空白结果 |
| 风险与收束 | 严重危险有世界内迹象，后果符合规则；记录可能解决、失败或放弃的信号，不预定唯一结局 |

预写场景、物品和线索提供事实与机会，不构成行动菜单。玩家可以换路线、提出未预写方法、放弃目标；KP 在事实内裁决。检定由当下的不确定性和有意义的后果决定，不能因为作者填了一个 DC 就必然掷骰。

检查时间线时把“某人说了什么”与“实际上发生了什么”分别计算。真正冲突须标出涉及段落和影响；开场知识不能通过编造另一段经历替正文补洞。涉及已固定故事锚点或版本时，按第 5 节处理。

## 2. 提前准备会影响因果的物品

从正文逐项提取文件、钥匙、信物、证据载体、工具、容器及危险关联物。对作者已经确定、会影响因果的关键物品，开场前就用已有类型建好 JSON，写明定义、位置或持有人、私有来源事实和相关角色知识。实例在开场还是发现时生成，按下表区分；不要等玩家搜索后才选择预设关键物品的藏处或真伪。

当前准备目录使用 `zhuwei.module-preparation/v1`，顶层为 `schema`、`catalogId`、`moduleRef`、`items`、`knowledge`。每件实物按以下分工填写：

| 字段 | 写什么、怎样检查 |
| --- | --- |
| `definition` | 已有 `ItemDefinitionV1`：稳定定义 ID、规则依据、外观与可执行效果。`causalBasisRefs` 引用本件 `fact.id`；集合字段遵守现有排序与去重要求 |
| `entry` | 实例 ID、数量、起始位置或持有人、所有权、可见策略。保管者不自动成为所有者，持有遗嘱不自动取得产业 |
| `fact` | 唯一来源事实、所在场景、关联 `clueIds` 和私有说明；记录藏处、文书真伪及来源，供授权上下文使用 |
| `materialization` | 明确为 `initial` 或 `onDiscovery`，按下表决定何时产生实例 |

| 准备方式 | 适用情形 | 状态路径 |
| --- | --- | --- |
| `initial` | 开场就必须追踪的实物，包括 NPC 私下携带的物品 | 定义、私有来源事实和实例一起进入 genesis；实例可见性仍由 Viewer 策略决定 |
| `onDiscovery` | 藏处已经确定、但尚未被发现的场景物品 | 定义和私有来源事实进入 genesis；实际发现时引用原定义及 `uniquenessBasisRef`，经已有 `materializeItem` 生成实例 |

“开场存在”不等于“玩家看见”，“发现时生成实例”也不等于“发现时才决定藏处”。`onDiscovery` 的 `entry` 是预留材料，不是已经出现在库存中的实物；实际位置由本次合法事务落定。

每件唯一实物的 `entry.entryId` 必须由现有 [uniqueItemEntryRef](../../app/_runtime/lib/rules/v2/item-authority-vnext.ts) 从 `fact.id` 计算；发现时继续使用同一事实作为唯一性依据。不要手写另一套描述性实例 ID，或让不同领取入口各生成一份。名称相似的两件实物与同一实物的多个别名也必须区分。

当前准备器只接收数量为 1、不可堆叠的唯一实物；初始位置支持已登记场景或该场景的已登记 NPC，`onDiscovery` 只支持场景位置。玩家开场装备走现有人物卡路径。堆叠物资、容器内部库存等超出此目录能力的内容，应沿对应权威类型补齐接入后验收，不能私加 JSON 字段冒充已支持。

物品定义的公开外观与秘密内容分开。逐项检查名称、描述、别名的投影和线索提示，避免“看到羊皮纸”顺带暴露“这是唯一真遗嘱”。拿到、看见、阅读、理解和相信是不同结果；纸张转移或毁坏不抹除角色已经取得的知识。

物品的开锁关系、诅咒、光照、攻击或消耗效果必须有可执行规则依据。自然语言里的“万能钥匙”“点燃后照亮酒窖”不能代替机械定义。当前目录只有物品和知识；已有危险、通路与 NPC 能力使用各自权威输入，不能仅写入 `fact.description` 就宣称具备机械效果。

尚未进入因果链的装饰细节可以保留为开放留白；KP 描写后按 SPEC 0001 保存叙述承诺，在被引用或产生因果作用前再固化。作者无需穷举整栋房屋的每件陈设。

## 3. 按角色准备开场知识

逐条回答：**谁知道、知道到什么程度、从哪里得知、何时得知、还有什么不知道**。同场景可见信息、私人经历和专业常识分别写，不能把作者真相页整段交给角色。

| 知识类别 | 作者应写出的依据 | 接收边界 |
| --- | --- | --- |
| 现场经历 | 角色确实在场看见、听见或接触到的内容 | 按实际开场地点与感知条件授予；异地角色不会自动听见大厅介绍 |
| 专业常识 | 角色卡中已有训练足以支持的通用理解 | 只给满足条件的角色；辨识训练不直接确认本案真伪 |
| 个人背景 | 已建立的身份、经历、关系及其具体信息来源 | 由可信角色前提支持；不按职业名称、姓名或临时自称猜测 |
| 来源主张 | 说话者或文献、内容、时间、知识依据与可信限制；谎言还要有动机 | 得知“某人声称 X”不等于确知 X；保留核验或证伪方向 |
| NPC 私人知识 | 自己做过的事、亲历证据、获告知的内容和基于证据的推断 | 每个 NPC 单独整理；共同阵营和同一模型都不代表共享知识 |

当前 JSON 的一条 `knowledge` 包含 `id`、`audience`、`kind`、`content`：

- `audience.kind = "openingPlayers"`：提供 `sceneId` 与 `anyProficientSkills`。空技能数组表示该地点所有开场角色；非空表示至少命中一项技能，地点条件仍须满足。技能 ID 来自服务端规范化角色卡。
- `audience.kind = "npc"`：提供明确 `entityRef`。此补充与故事圣经原有初始知识合并，因此还要交叉检查 `declaredUnknowns`，不能用补充绕过未知边界。
- `kind` 使用已有四类：`canonicalFact`、`sensoryEvidence`、`sourceClaim`、`characterInference`。只有有依据、可授予该角色的已知事实使用 `canonicalFact`；猜测或说法不能升级成全知事实。
- `content.description` 写角色实际得到的信息；`acquisition` 写取得经过和时间条件；`sourceRefs` 使用校验器可解析的场景、NPC 或已准备事实等引用。线索关联写在物品的 `fact.clueIds`，不要假定任意文本 ID 都能作为知识来源。

通用训练常识可以没有具体场景事实来源，但 `acquisition` 必须说明已有训练。运行时把描述与取得依据转成现有可叙述的 KnowledgeRecord，将目录和来源引用留在 `provenanceChain`，按持有人私有投影。`layer: full` 只表示这条已授予信息完整，不表示角色掌握整个案子的真相。

当前目录的自动选择条件只有 NPC 身份、玩家开场地点与技能；任意背景、语言、感官能力和个人经历尚未通用接入这些条件。写作时仍须分析它们会影响什么信息，并标出需要的角色前提或能力接入；不要给所有玩家发送背景专属知识来掩盖缺口。

开场信息应让玩家理解自己在哪里、现场发生了什么、能与谁互动，并保留私人信息的单独受众。亲属关系、委托、债务和个人经历须有已确认角色前提；是否调查、相信谁、如何回应由玩家决定，不用“你感到必须帮助她”替玩家决定情绪与行动。

## 4. 让线索、NPC 和危险能继续运转

将物品表、知识表和正文逐项对照：知道钥匙用途的人是否有获知依据，拿到文件的人是否实际读过，NPC 的下一步是否依赖尚未知晓的秘密，危险是否已有迹象和可执行定义。

关键结论准备不同来源的证据和合理核验方式，避免一个物品丢失或一次骰点失败后只剩重复掷骰。基础观察诚实提供；深入调查可以改变理解、完整度、速度或代价。任务与机会仍可失败，不保证每条路线始终开放。

NPC 的下一步写成基于目标、知识、资源与虚构条件的行动意向。世界变化后可以修订，执行仍通过同一 Rules/Room 路径。冷场时先重新说明已知局面，再提供符合事实的机会；危险只在虚构条件满足时兑现，现实思考时间和固定对话轮数不是期限。

预设危险至少说明触发、可感知迹象、调查或解除依据、影响范围、规则后果和持续时间。线索文本不能兼任伤害结算，玩家改变方法也不能成为追加机关的理由。每场结束时检查问题是否已经回答、核心冲突是否已经解决或放弃，允许真实收束。

## 5. 核对版本、接入与恢复

1. 从当前 Registry 取得精确 `moduleRef`，不凭文件名猜 hash。目录用独立 `catalogId` 与规范内容 hash 标识，不与应用版本或 `WRITING_REVISION` 混用。
2. 校验 JSON 原文无重复成员，所有 ID 唯一、引用存在、位置与 NPC 开场地点一致，并通过 `validateModulePreparation` 及已有物品校验。校验失败就修作者材料，不能运行时清洗成另一份成功结果。
3. 核实目录已登记到 `preparation.ts` 并由 `RoomDurableObject.initializeAuthoritative` 消费。只有创建新 genesis 时准备目录；后续行动、重试和恢复读取房间持久状态。`openingPlacement` 是历史起始位置，不是当前持有人查询。
4. 已使用目录内容变化时使用新的目录 ID；既有房间继续使用自身 genesis，不重新读取新 JSON 补发物品或知识。更换目录 ID 不能绕过故事锚点版本约束。
5. 涉及已固定核心真相或第二模组版本时，先按 SPEC 0006 核清现役房间与协议边界，再按仓库授权路由处理。当前只注册一个模组版本；普通补充不自动授权迁移或重解释房间。

完成标准是“材料经真实新房初始化保存，后续从同一状态取回”。单独放置 JSON、在 Prompt 中粘贴清单，或把补充写进 Markdown，都不足以证明运行时已采用。

## 6. 交付与验收

改动前选择覆盖本次变化的代表性矩阵，至少包含用户要求的样例、一个结构不同的样例及最高风险边界。当前物品与知识准备可参考：

| 验收维度 | 代表性路径与应有结果 |
| --- | --- |
| 初始与发现 | NPC 持钥、场景文书与隐藏盒内文件共用定义和 Rules 路径；隐藏文件在真实 `prepare` 中能取回已有定义与来源 |
| 私有与共享 | 同场角色技能不同、另一角色异地、NPC 有私人经历；只向符合条件的 Viewer 授予信息 |
| 唯一性 | 初始实物不能用同一来源再次生成；隐藏实物发现一次后重复请求不会复制 |
| 错误输入 | 重复身份、错误模组引用、不存在的场景、持有人或来源被拒绝 |
| 恢复 | ACK、重复初始化、DO 驱逐与 replay 保留同一库存和知识，不重新发放 |

当前入口为 [module-preparation.test.mjs](../../tests/module-preparation.test.mjs)、[authoritative-opening-v2.test.ts](../../tests/authoritative-opening-v2.test.ts)；涉及原故事圣经时参照 [module-npc-v2.test.mjs](../../tests/module-npc-v2.test.mjs)。按 [AGENTS.md](../../AGENTS.md) 选择本次直接需要的检查，已有行为证据足够时不另建重复测试。

交付应包括更新后的故事或目录材料、对应的剧本补充说明、实际覆盖的矩阵与未覆盖项，并在 [执行日志](../refactor-log.md) 追加记录。修改通用写作约定时更新本文，实例细节留在剧本补充中；通过 README、repo map 和 AGENTS 的入口保持可发现性。

只改 Markdown 时检查目标段落、链接、规格一致性和 `git diff --check`，不重跑代码测试。修改 JSON 或初始化逻辑时验证相应行为链；本地检查、真实模型连续游玩和生产部署分别报告，不能相互代替。
