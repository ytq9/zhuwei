- 日期：2026-09-08。

- 状态：用户已认可并授权实施的模块化安排；共享 Interface 和实施证据见并行协调记录，不代表能力已完成。
- 代码观察点：cloudflare 分支，HEAD e657162，包含工作区正在进行的其他修改。源码导航描述本次观察到的接缝，实施前需重新核实。

## 1. 总体安排

**保留 Room Action 与 Rules 两个系统级 Module，在 Room Action 内增加 Story Creation 和 Story History 两个内部 Module；创作配方负责可替换的方法，宿主负责事实、权限、时间、调用预算和恢复。**

这里的 Module 是具有 Interface 与 Implementation 的职责集合，不要求独立进程、独立 Worker 或常驻 Agent。内部可以继续拆分，但外部调用者不需要知道具体提示词、模型调用步骤或资料存放位置。

新故事沿现有“准备上下文 → KP 提案 → Rules 验证 → Room 原子提交 → Viewer 投影 → 叙述”链路接入。进入游玩后，KP 继续理解自由行动、判断可行性、扮演人物和安排场景；故事准备提供依据与选择空间。

本方案沿用 [ADR 0006](../adr/0006-two-deep-modules-and-one-action-transaction.md) 的系统级分工，并使用其内部接缝承载新能力。历史开团需要扩充可信房间生命周期与 Rules genesis 合同，正式实施时记录直接 ADR；不通过更正旧团或灾难恢复接口伪装新开团。ADR 中旧 Legacy 描述服从当前 AGENTS 与已裁定规格的退役决定。

### 1.1 依赖与运行方向

~~~mermaid

    Action --> Creation[Story Creation：完整故事准备]

    Context[宿主 Context Adapter：授权材料与依赖] --> Creation
    Jobs[宿主作业与调用账本：预算 / 恢复] <--> Creation
    Creation --> Package[版本化准备包与评审结果]
    Package --> Admission[宿主接入 Adapter：生成正常 KP 提案]
    Action --> Admission
    Admission --> Rules[Rules：step / project / replay]
    Rules --> Authority[Room Authority：提交事实与保存结果]
    Authority --> Views[按 Viewer 投影与叙述]
    Authority --> Due[到期计划与活动工作项]
    Due --> Action
    Authority --> Archive[现有归档与准备资料归档]
    Archive --> History[Story History：导出 / 历史起点准备]
    History --> Genesis[可信新房间初始化与 Rules 验证]
    Genesis --> NewRoom[新 Room Authority：独立后续历史]
~~~

图中的框有不同职责，不表示每个框都要建立一个新 Module。调用全部留在当前 Worker 与房间体系内；图中的归档是不可变副本，不能裁决正在游玩的房间。

### 1.2 职责清单

| 安排 | 承担什么 | 不承担什么 | 变化集中在哪里 |
| --- | --- | --- | --- |
| Room Action，沿用 | 理解玩家意图、处理到期工作、决定创作时机、主持、聚光灯、提交与投递恢复 | 把故事路线当玩家行动白名单 | 房间编排及直接 KP Adapter |
| Story Creation，新增内部 Module | 将创作目标、授权世界材料与配方转为完整可玩的准备包，完成评审及有界修订 | 直接写世界、给 NPC 全知、代替 Rules 掷骰 | 创作 Implementation |
| 创作配方，可组合资料 | 提供调查、利益冲突等方法，规模要求、关联策略、材料与专项评审 | 私有 NPC 状态、任意代码执行、绕过预算调用模型 | 配方资料与受信任注册表 |
| Context / Admission Adapter，宿主接缝 | 取得授权事实、匹配能力、转接正常提案；映射版本和错误 | 自建规则解释器或吞掉事实冲突 | 宿主 Adapter 与相应公开合同 |
| 故事关联记录，宿主数据 | 关联准备包、人物、事实、计划、阶段问题和真实结果，支持继续主持 | 复制 NPC 库存、知识、位置或执行另一个任务状态机 | Room 持久化与派生查询 |
| Rules 与 Room Authority，沿用并扩展必要语义 | 验证、随机、时间、原子提交、世界事实、知识、计划及投影 | 决定故事必须精彩、强制指定结局 | Rules 内部与 Room 权威存储 |
| Story History，新增内部 Module | 准备权限正确的导出，以及带来源证明的历史新分支材料 | 改写原团、自动升级解释器、把原团未来当新角色知识 | 历史选择与导出 Implementation |

**当前不另建“支线运行引擎”“NPC 记忆库”“世界模拟器”三个并行权威。** 它们涉及的有效行为已经分别属于正常主持、角色知识与计划/时间合同。故事关联查询先作为内部数据能力；只有出现独立复杂度和真实消费者时，再提取内部 Module。

## 2. 四组需要稳定的 Interface

以下名字表达语义，不冻结 TypeScript 类型、函数名或 DTO。Interface 同时包含权限、顺序、错误、预算和版本要求。

### 2.1 Story Creation Interface

建议提供一个“准备或继续准备故事”的操作。首次与恢复使用同一作业身份；查看进度由宿主作业读取处理，不把模型私有步骤暴露给页面。

| 输入／输出 | 必须表达的内容 |
| --- | --- |
| 创作请求 | 宿主分配的 jobId、来源根行动/世界事件、目标与触发依据、规模/关联/玩法、已选故事或机会、授权作用域、预算凭据 |
| 世界材料 | 精确模组与 runtime 引用、锚点、相关事实与叙述承诺、人物当前处境、各主体认知切片、虚构时间、可用机械能力、依赖集合 |
| 配方绑定 | 各配方版本与内容摘要、组合参数、必需检查、允许的创作工作流；作业开始后固定 |
| 完成结果 | 不可变版本的准备包、可追溯评审报告、实际使用材料、未决适用项、宿主记录的消耗 |
| 其他结果 | 无需新故事、需要上下文、需要预算、资料过期、需要修订、能力不支持、调用失败或调用结果不确定 |

Story Creation 通过注入的 Context、模型调用及作业 Adapter 使用宿主能力，不导入 Room DO、数据库驱动或 Rules 私有实现。模型提出的资料需求由宿主校验作用域，不能成为任意读取指令。

“无需新故事”只表示本次无需完整创作，不能被解释成世界里没有某人、没有危险或没有这段历史。普通问答、空白结果和即时小事继续由正常 KP 处理。

### 2.2 Context 与接入 Interface

- **Context Adapter** 根据真实依赖建立材料闭包：相关人物、地点、组织、经历、知识、承诺、资源、计划、叙述承诺及集合成员版本。它分别标明已知、局部否定、开放留白、明确未知、歧义和技术不可用。
- **Admission Adapter** 接受准备包的确切版本和本次待生效材料，映射到当前受支持的提案合同。新对象用待接入的局部引用关联，最终身份与执行依赖由宿主正常路径分配和验证。
- 语义审查报告绑定候选正文、输入约束及版本；提交前由权威路径检查绑定和实际读取集。相关对象改变或集合新增成员使相应报告失效，无关地点变化不要求整包重写。
- 机械可执行性、读取集验证、随机与事件创建继续属于 Rules/Room。Adapter 不能自行推导一套相同规则、生成自由状态补丁或修改模型决定使非法提案通过。
- 接入依赖不能只由模型自报。宿主与 Rules 要覆盖本次实体、知识持有者、相关事实集合、时间及资源等实际约束；跨地区需求须扩展同一权威查询能力。

### 2.3 创作配方 Interface

配方首先实现为**版本化数据与受信任写作说明**：说明适用情境、输入需求、输出要求、可组合维度、专门评审以及所需宿主能力。运行时不自动执行 SKILL.md 引用的脚本，也不给素材包网络或数据库权限。

同一准备包可以组合一个主要创作方法及若干约束，例如：

| 配方组合 | 改变的内容 | 共同产物 |
| --- | --- | --- |
| 地方独立 + 短篇 + 利益冲突 + 既有关系 | 各方目标、可交易资源、妥协成本、公开压力、离开后的发展 | 同一故事准备包 |
| 主线相关 + 短篇 + 调查 + 制度档案 | 核心结论、独立证据来源、发现与传播、证伪和替代调查方法 | 同一故事准备包 |
| 角色个人 + 长篇 + 救济/护送 + 阶段收束 | 持续关系、阶段问题、资源与路线变化、个人关注和聚光灯 | 同一故事准备包 |

配方组合使用明确字段和适用规则。冲突项在调用前报告或由宿主选择适用方法，不依赖加载顺序覆盖。产品不变量、内容边界、锚点和事实具有硬约束地位，配方的修辞与节奏偏好在其中工作。

第一阶段至少让前两种结构不同的配方经过同一 Interface。无需为每种玩法分别创建 Agent，也不要求“调用次数 = 配方数量”；写作 skill 和模板可以成为配方材料，执行、评审调度与预算仍由宿主安排。

### 2.4 Story History Interface

提供“准备导出”和“准备历史新分支”两类操作，调用者提交可信授权、精确来源、目标范围与起点意向。结果是受限记录、系统开团材料，或带原因的不可恢复结果。

历史 Module 使用宿主提供的归档读取、受支持解释器和历史投影能力。创建新 Room、分配新身份以及提交 genesis 由可信房间生命周期入口完成；它不持有向任意房间写状态的通用能力。

## 3. 故事准备包与宿主数据

### 3.1 准备包的内容安排

| 内容区 | 保存什么 | 生效方式 |
| --- | --- | --- |
| 依据与目标 | 来源、故事规模、世界联系、内容边界、相关版本和事实依赖 | 限制本次创作与接入 |
| 核心局势 | 起因、核心真相、冲突问题、已成立条件、开放留白 | 区分已有事实和新候选，不能混作正史 |
| 人物与关系 | 既有实体引用；新人物候选；各自目标、顾虑、资源、关系与有限知识 | 复用或经正常实体/事实/知识路径接入 |
| 场景与证据 | 场景问题、空间、可互动物、线索来源、合理介入机会、必要机械定义 | 首次产生因果作用前补齐并固化 |
| 发展与收束 | 人物打算、无人介入的发展条件、可察觉痕迹、阶段成果和结束依据 | 打算经本人认知形成合法计划；未来结果待执行 |
| 主持材料 | 演出建议、声口、可概括内容、回主线或继续长篇所需的关联信息 | 供 KP 主持；不执行场景顺序或限制玩家方法 |
| 审查与绑定 | 完整性、语义与玩法报告、候选版本、已接入事实/计划/Receipt 引用 | 过期时复核受影响内容；保留可追溯来源 |

完整准备意味着故事起因、局势、行动空间、发展条件与收束边界都可主持。它不要求枚举所有路线，也不允许将长篇仅保存一个标题和开场后标为完整。长篇以后扩写的细节继续服从已经确立的核心材料。

准备包和玩法不同于执行图。场景之间的关联可以描述线索和可能去向；不能据此自动让玩家移动、接受任务、完成承诺或经历特定结局。

### 3.2 分开记录三种状态

| 状态维度 | 示例 | 决定什么 |
| --- | --- | --- |
| 创作作业 | 收集材料、生成、评审、就绪、等待、失效、失败 | 还需要做哪些准备、还能消耗多少预算 |
| 玩家参与与当前镜头 | 尚未接触、已接触、正在介入、暂离、退出；当前是否聚焦 | KP 关注什么、玩家取得过什么参与经历 |
| 世界中的冲突 | 仍成立、已经解决、失败、机会消失、实际停止 | 人物与环境现在处于什么局势 |

这些是建议语义，不是一份冻结枚举。玩家离开不改变已经开始的 NPC 计划；创作失败不代表世界事件失败；故事退出聚光灯不等于冲突结束。参与记录引用真实行动，不能额外授予物品或知识。

故事关联记录只指向人物与事实，NPC 的知识、伤势、位置和资源永远读取当前分支中的同一对象。一名 NPC 可以关联多个故事，具体行动仍受其位置、资源和同时进行活动的规则限制。

### 3.3 持久化归属

| 数据 | 推荐归属 | 恢复与导出要求 |
| --- | --- | --- |
| 静态圣经、配方与评审规则 | 当前受信任静态目录与构建产物 | 版本固定；不回写静态 NPC 初始知识 |
| 作业、候选、冻结请求、评审、调用与预算账本 | Room 管理的非正史作业存储，先使用现有 DO SQLite 能力 | 重启继续同一作业；私密材料不进入玩家进度、普通日志或亲历记录 |
| 已接入的准备包与故事关联 | Room 保存版本化资料；生效引用绑定提交结果 | 世界 replay 使用世界事件；继续主持需要的准备资料也必须纳入相应归档包 |
| 实体、世界事实、知识、计划、承诺、Activity | Room 权威事件及其世界状态 | 经 Rules 验证、原子提交和按 Viewer 投影 |
| 索引、摘要、归档副本 | 当前派生查询及 D1 归档职责 | 可重建；不能代替事实读取或正史写入 |
| 玩家亲历文本 | 原有 ViewerKey 专属 Room 记录 | 仅导出该观察者实际获得且仍可取得的正文；不由事件补写旧旁白 |

DO 保存不代表数据自动成为世界事实，作业表与正史必须有明确性质区分。准备包中的事实副本是绑定版本的材料，不能拿来覆盖最新 NPC 状态。

现有归档只具备自己的固定字段。新增完整准备资料需要扩展归档合同与缺失检查，不能声称保存世界事件就自然保存了全部主持材料。草稿清理只处理没有生效且没有保留义务的作业材料；已公开承诺、已生效资料及恢复所需版本不随配方停用而删除。

## 4. 从触发到游玩的完整流程

1. **先处理真实世界。** Room Action 处理本次相关的到期工作和玩家意图，读取已有故事关联；KP 判断是普通回应、继续现有故事、形成介入机会，还是投入完整创作。
2. **确定范围与预算。** 宿主依据真实触发、已有故事和配置建立稳定作业身份，绑定配方、规模、权限、预算与恢复点。单纯问一句话不自动接受委托，也不自动启动长篇生成。
3. **准备世界材料。** Context Adapter 取得所需锚点、人物、事实、承诺和跨地点依赖。扩展读取时重建一致的材料绑定，不混用不同时间的矛盾快照；取得不到必需材料时保留明确等待或失败结果。
4. **完成故事准备。** Story Creation 写出核心局势、参与者、场景、证据、发展条件和收束；复用已经存在的准备。以主体引用和触发依据识别同一机会，避免为相同询问反复生成不同真相。
5. **进行完整性与质量审查。** 硬约束失败先定位材料；语义冲突、实质不确定或不可执行能力不能进入接入步骤。修订有界，保留失败结果与成本。
6. **接入当前需要成立的内容。** Admission Adapter 将候选交给正常 KP/Rules/Room 链路；同时成立的事实、人物知识、实体与关系依赖形成原子组。准备完整不等于提前执行全部未来剧情。
7. **按真实结果呈现。** 只有提交后的相应 Viewer 材料才能进入该角色的叙述。NPC 开口、证据出现或危险影响行动前，其因果依据已成立；不会等“正式接任务”后再决定真相。
8. **按自由行动继续。** 下一轮取回准备材料和最新世界事实。第三种方法、提前解决、失败、离开、协商或重返都走同一行动合同；已收束的故事保留后果。

每次接入以当前因果闭包为原子单位。可以保存整本准备但只接入当前相关内容；尚未接入的候选不能提前产生消息、资源或知情者。已接入内容继续保留，后来扩展失败只能使该扩展等待，不能倒退已发生的事件。

接入身份绑定作业、准备包版本和本次材料范围，Room 将相应 Receipt 与生效引用一起保存。提交成功但作业进度尚未更新时，可以由保存的 Receipt 对齐进度，不能再次接入或重复创建 NPC。玩家端只取得必要的非内容进度，不能从任务名、评审错误或等待原因获知秘密故事。

创作产生的等待属于技术状态，不推进虚构时间。其他地点在因果上独立的合法工作仍按既有房间并发规则处理，不因一份长稿锁住整个世界。

## 5. 质量控制如何成为框架能力

质量检查由宿主强制执行的基础要求与配方增加的专项要求组成。配方可以增加检查，不能关闭事实、秘密、公正、玩家决定权或机械合法性检查。

| 检查层 | 检查内容 | 结论及限度 |
| --- | --- | --- |
| 结构与完整性 | 材料齐备、稳定引用、条件明确、必需定义可表达、关键证据有来源 | 证明可解释和准备充分；不证明故事有趣 |
| 世界语义 | 时间、年龄、经历、制度、地理、目标、已知未知、来源与叙述承诺是否矛盾 | 返回候选段落与约束依据；冲突和重要不确定阻止相应事实生效 |
| 跑团可玩性 | 选择能否改变结果、信息是否支持行动、失败是否形成局面、是否存在检定墙、能否结束、多人参与 | 返回可修订的具体问题；不把反转数或成功率当统一质量分 |
| 正常权威接入 | 权限、读取集、定义、资源、空间、时间、知识取得与原子性 | Rules/Room 决定是否可提交，不能被文学评审覆盖 |

确定性检查处理结构和已结构化矛盾；自然语言一致性使用有证据定位的语义审查，实际玩法需要代表性人工/游玩评审。生成者自己填写 compatible 或一个 hash 不能代替这些检查；另一次模型评审也不是“绝无矛盾”的证明。

运行时必需审查纳入预算；上线前通过固定样例、真实模型批次与人工评审校准。记录整批的一次通过率、修订率、冲突与秘密错误、完整准备消耗、被实际游玩的比例和复用情况，报告样本量与失败材料，不筛选成功作品宣称稳定。

## 6. NPC、幕后世界与承诺如何接上

### 6.1 同一个 NPC 的知识与经历

故事准备引用既有 npcRef，并声明新事实候选、实际发生时间、知情者、取得时间/依据及取得范围。宿主复用现有 WorldFact、Knowledge 与 SourceClaim 的语义；必要扩展进入同一 Rules 合同。

例如船夫可以因昨日亲历征用而知道扣船过程，随后在当前对话中告诉玩家。“征用发生”“船夫知道”“船夫说了什么”“玩家听到了什么”各有依据。另一名 NPC 只有实际接触或接收消息后取得相应知识，KP 的写作材料不自动授权给他。

补充以前未记载的经历必须检查相关人物一生中已有的约束，不能只看当前场景里出现的人。已经明确不知道的事情不能补写成早已知道；后来确实获知可以更新。当前 world-facts 的局部场景材料是起点，跨地区和跨故事的约束闭包需要补齐。

创作可以准备 NPC 的行动方向，但已存在 NPC 的实际计划形成与修订要使用本人的认知投影。不能把包含全知秘密的整份准备包直接交给 NPC 决策，再仅靠一句“不要使用秘密”保证隔离。

### 6.2 幕后发展继续使用计划与虚构时间

无人干预的发展写成目标、前提、准备尝试的下一步、期限/触发和可察觉痕迹。相应计划通过正常形成合同生效，之后由既有到期工作路径唤起 KP、Rules 与 Room。

不额外建立每隔现实几分钟生成故事的定时循环。可因虚构时间、势力行动或已提交事件发现新的创作需要；重要且相关的幕后冲突能够成为完整故事，普通日常无需逐人模拟。

已到期且影响当前裁决的计划必须结算或明确停在稳定等待点。预算调度可以延后可选的远处创作，不能默默跳过已生效计划。信息传播需要媒介、耗时和接收者；跨地点结果必须满足因果前沿。

### 6.3 承诺由既有领域合同解释

故事参与、NPC 内部计划和对他人的承诺是三个不同对象。是否违约、能否延期/修改/取消以及知情者的反应由相应承诺合同和实际事实决定；某计划结束不能自动推出承诺履行。

故事 Module 只引用这些结果并安排后续主持，不维护另一套声望扣分或违约计时器。未承诺的好奇、拒绝或技术故障没有自动违约责任，创作预算也不进入世界内处罚。

## 7. 预算与中断恢复

### 7.1 一条可追溯调用链

每次实际调用关联房间、来源根行动/世界事件、创作作业、阶段、尝试与调用身份。上下文准备中的付费步骤、创作、审查、修订、接入提案和叙述均计入相应宿主预算；不同工作量可以使用不同配置，但不能开插件私账绕过共同额度。

完整创作启动前检查是否具备所选规模与必需审查的预算。复用材料、减少可选扩写和按需读取是成本控制手段；削掉决定性真相或省略审查不能让失败任务变成“完整”。模型、金额、token 上限、尝试数及延迟目标留给后续实测配置。

预算预留和调用登记需要持久化与并发校验，不只用请求内计数器。真实 usage 缺失或结果不确定要如实标明，不能记作零费用或重复释放预留。重试请求只能恢复保存的阶段，不能重新获得一份全新预算。

当前 vNext 提案调用账本绑定特定上下文、阶段、工具和有限序号。故事创作需有独立、版本化的工作流绑定；复用其可靠调用原则与宿主能力，不直接放大旧提案序号或把长稿塞入行动修复循环。

### 7.2 恢复规则

| 中断位置 | 恢复动作 |
| --- | --- |
| 尚未请求模型 | 复用 jobId 和预算预留，重新校验任务资格及上下文 |
| 结果已保存，后续步骤未完成 | 使用保存的确切结果继续审查或接入，不重写该阶段 |
| 请求已发出但结果未知 | 保留不确定状态；按 Provider 可证明的查询/幂等能力处理，不能靠再次采样假装恢复 |
| 语义或相关依赖冲突 | 定位受影响候选，重新取得一致上下文并有界修订，生成新的候选版本 |
| Rules 拒绝或接入前崩溃 | 不发布该原子组的成功；按保存的诊断和提案生命周期恢复 |
| 世界已提交，叙述未发布 | 从同一 Receipt、事件范围和冻结受众恢复投递，不重掷、重放行动或再创建事实 |

Provider 结果未知后如确需新的付费尝试，它必须成为显式的新尝试并计入原作业总额，同时防止迟到结果形成两次接入；具体可支持机制随 Provider 合同实现，不能宣称端到端外部调用恰好一次。

LLM 调用在 Room 数据事务之外进行。每次推进有界，保存检查点后由后续请求或宿主已有工作恢复机制继续；不能依赖进程内后台 Promise 活着。现实时间只用于技术租约和重试，不推动故事时间。

## 8. 导出与历史新分支

### 8.1 分开三种导出

| 产物 | 读取资格 | 内容 |
| --- | --- | --- |
| 玩家亲历记录 | 该 ViewerKey 的合法访问者 | 实际取得的正文及获准的结构化信息，无法补出遗失或未亲历文本 |
| 结构化世界记录 | 对应目的的可信授权 | 已提交事件、定义、来源与时间；提供给普通玩家的部分仍经授权投影 |
| 历史开团包 | 受信任系统开团能力 | 所选起点的完整因果材料、准备资料、解释版本和新身份初始化依据 |

系统开团包可以保留 KP 主持所需秘密，但不直接暴露成玩家下载文件；用户可取得授权的开团引用或受保护传递结果。所有者/房主身份不能自动解锁全知记录，原房间服务 capability、账号会话、密钥和旧 Viewer 投递授权不进入包。

### 8.2 一个历史起点需要两种定位

历史新分支、同一房间分头行动的 FictionTimeline，以及纠错使用的因果分支分别处理。历史新分支建立新房间权威和来源关系，不直接复用旧团的 activeBranchId 充当新团身份，也不修改原团的活动分支。

先冻结**来源正史版本**，再选择**历史因果起点**：前者说明采用原团哪一条有效历史及哪次归档，后者说明新故事从哪些地点的哪个已成立时刻开始。

初版推荐支持可以证明完整恢复的离散起点：位于完整提交边界，具有所需事件、定义、因果前沿及可处理的活动/待决状态。未实现活动中途恢复的切点应明确不可选，并给出已验证的可选点；不能暗中把时间挪到方便的位置。

地区/事件选择首先决定新身份与开场焦点。首版优先保留该起点完整世界状态与资料闭包，不按场景字段任意裁剪其他地区的因果依赖。以后若需要小型区域包，再增加可证明完整的依赖提取。

### 8.3 历史准备流程

1. 校验来源权限、不可变归档头、当前有效分支、完整事件、精确解释器/模组/定义版本。
2. 通过受支持的 Rules replay 与历史选择能力取得起点状态；检查所选多地点时间和因果闭包。不能拿最终状态倒改时钟，也不能仅按一个事件序号处理所有地点的时间。
3. 检查后来补录、实际发生于起点之前的经历。分别表达发生时间、固化时间和知识取得时间；起点之前确实成立的内容可作为经验证的历史补充，起点之后才获得的知识不得提前授予。
4. 补充材料必须与起点的已有事实和选定正史版本一致，由可信历史构造与 Rules 初始化共同验证。不能重放整个未来事件来取出其中一条旧经历，也不能顺便继承未来的物品、伤害、计划结果或秘密。
5. 生成版本化 Branch Seed，包含来源与切点证明、初始状态及定义、适用准备资料、未决世界计划、身份映射和新角色的合法初始依据。已在原团未来执行的结果不作为新分支的必达结局。
6. 通过可信开房入口创建新 roomId 与 runtime epoch，使用注册支持的 genesis 合同验证并建立新权威。新席位、控制者、Viewer 与投递身份重新建立，不复用原团访问凭据或消费原团预算。
7. 新分支重算之后的行动与计划结果，保留来源关联；原团保持不变。原角色若仍存在，其世界内身份按起点保留，但同一账号不自动取得其控制权或记忆。

继承对象在新分支中有明确身份映射，所有物品所有者、知识持有者、关系、计划和定义引用一并保持一致；同一分支内不会因故事再次使用而复制 NPC。是否使用新 ID 或分支命名空间由 genesis 设计确定，不能随意修改签名事件中的 roomId 来完成导入。

当前 worldFact 的 occurrence 包含自然语言，现有归档恢复也以灾难恢复为目的。它们不足以自动证明任意过去时点的状态。后续需要可靠的历史时间表示、补录筛选和新分支 genesis；无法确定先后关系时拒绝该起点，不从文字猜测后冒充准确恢复。

历史开团的默认新身份按所选起点具有独立来源，不能继承旧角色的全部物品、知识、债务或权力。原团起点之后的实际结果可以留在来源档案供审计，但不得作为新角色知识或要求新世界照演的脚本。

## 10. 版本、替换与不可分开的部分

需要分开记录的版本轴包括：配方内容、故事准备格式、创作工作流、机械规则/runtime manifest、模组内容和历史开团格式。配方升级不自动改变存量事实或房间机械语义。

已完成准备保存可由平台解释的产物和必要版本。停用调查配方后，已生成调查仍能主持；已开始作业根据保存的精确配方/工作流继续，或明确保留等待，不能暗换新配方重新抽故事。机械回放和已提交叙述恢复不调用旧写作插件重建历史。

配方选择与替换只发生在该房间已注册允许的创作合同内，作业绑定之后保持固定。新增工作流若超出现役 runtime/Profile 的允许范围，需要正常的新版本与数据责任决定，不能利用“插件升级”静默绕过房间创建时固定的 manifest。

| 可以集中替换 | 必须共同遵守 |
| --- | --- |
| 调查/社交等创作方法、规模与关联偏好、场景写作、专项评审 | 故事锚点、事实身份、明确未知、内容边界、玩家决定权 |
| 模型调用 Implementation 与提示词组织，受现役版本合同约束 | 宿主身份、预算、调用记录、数据权限与恢复语义 |
| 当前 KP 提案形状的 Adapter | Rules 可执行能力、原子提交、知识/关系/资源语义 |
| 归档编码和历史准备 Implementation，受持久化合同约束 | 可恢复解释版本、来源证明、时间与因果、新身份权限 |

这些共同依赖有意保留。例如新增“誓约约束”的真正机械效果会涉及 Rules，跨地点消息涉及时间与知识，历史重开涉及 genesis 与归档。把它们完全移入配方，会产生第二套世界规则。

## 11. 实施顺序与验收安排

实现按三阶段推进，与能力合同的交付边界对应。第一阶段内先贯通实际纵切，再扩展同一机制；第一阶段完成不代表幕后与历史分支已经交付。

| 阶段 | 交付内容 | 对应合同与代表性证据 |
| --- | --- | --- |
| 第一阶段：创作与当前世界接入 | Story Creation、两种配方、完整准备与质量门、现有 NPC、新人物、故事关联、预算/恢复、短篇与分阶段长篇 | C01–C05、C07–C09、C11；A01–A07、A09–A10、A13。先以药船冲突贯通真实本地输入到 Viewer，再让档案调查走同一 Interface，最高风险覆盖矛盾或秘密拒绝 |
| 第二阶段：幕后与跨地点 | 创作所需的异地材料、有限知识计划、到期结算、消息传播、暂离/返回与收束的组合 | C06 及跨地点关联条款；A08，并复核 A07、A09 在真实虚构时间下的行为 |
| 第三阶段：导出与历史新分支 | 准备资料归档、权限正确的导出、历史因果起点、补录时间、新身份、可信 Branch Seed/genesis | C10；A11–A12，包含原团不变、新团结果分歧、未来秘密不继承及缺失材料拒绝 |

第一阶段的准备格式就要保留故事来源、精确人物引用、时间性质、定义版本、知情者及事实/计划的区别；调用结果与准备包也需要可靠保存。历史开团可以后做，但这些依据不能等最后阶段再从旁白猜补。

开发期验证以真实 Interface 为表面：确定性行为验证状态/权限/恢复，受控真实模型批次验证创作产物，人工或实际游玩评审验证可行动性和故事质量。读取已有测试是接缝调查，不能作为本轮运行通过或未来模块已经完成的证据。

在进入编码前，下一份实施规格应具体化第一阶段的准备包最小字段、宿主 Interface、作业阶段、语义检查报告、存储/归档影响和代表性测试；数值预算根据准备样例测量后设定。本框架不要求先建插件市场、多个常驻 Agent、独立世界服务或跨团共享活跃正史。

## 12. 本次交付与设计限度

本次完成整体职责、Interface、数据归属、触发/接入/游玩链路、质量门、预算恢复、NPC 与幕后组合、历史新分支及实施次序的设计。没有实现这些新 Module，也没有运行模型批次或行为测试。

本方案服从 [SPEC 0001](../specs/0001-llm-kp-responsibility-contract.md)、[SPEC 0006](../specs/0006-module-npc-and-faction-protocol.md)、[SPEC 0007](../specs/0007-multiplayer-room-and-fiction-time.md)、[SPEC 0008](../specs/0008-long-campaign-lifecycle.md) 与 [SPEC 0010](../specs/0010-observer-specific-presentation.md)。具体导入/genesis 与版本合同若需要改动已裁定条款，须定位实质变化后按项目规则处理；本提案本身不修改这些规格。
