## 3. 能力合同与关键区别

使用者是 KP；玩家继续自然语言行动，不填写内部档案。对象包括普通装备、工具、消耗品和带机械效果的物品，支持名称/外观变化、物品属性变化、效果参数与使用成本变化，以及已有定义直接复用。

“档案”需要足以合成正式 ItemDefinition，带机械的物品还须绑定完整可执行 Ability。介绍文字或物品名称列表不算完整档案。

区分三件事：

| 概念 | 职责 |
| --- | --- |
| 可复用模板档案 | 版本固定的通用定义、效果依赖、用途和查找信息；不带某个玩家的持有状态 |
| 派生物品定义 | 从选定档案与本次差异合成、验证后固化的完整定义 |
| 实物实例 | 当前世界里的这一件/这一堆东西，记录数量、归属、位置、充能、耐久等实际状态 |

“无需重新创建”指 AI 无需重填完整档案；需要变体时，系统仍生成并保存正式完整定义。创建新实物仍走物化与库存生命周期。基础档案的更新不回溯改变已经生成的物品。

模板存在只说明“这种物品如何定义”，不证明场景中已经存在、角色已经持有或获准取得。新物品的存在性继续服从故事事实与开放留白授权。

## 4. 目标流程

```text
自然语言行动 / KP 创作需要
→ 查找相关物品档案与效果档案
→ KP 选择准确档案；直接复用，或填写实际差异
→ 服务端从冻结版本合成完整 ItemDefinition / Ability
→ 同一本地校验、Rules 验证、Room 原子提交
→ 创建或操作实物实例
→ Viewer 投影与叙述
```

填写示意，不是待照抄的协议：

```text
参考档案：治疗药水
修改名称：老巫医的苦味药水
修改外观：深绿色，浓烈草药味
修改治疗量：2d4+4
其余使用、目标与消耗规则：继承
```

模型只提交本次有意义的选择。固定 ID/hash、派生字段、完整定义展开和机械执行归服务端。差异需要类型明确且可验证，最终状态与事件保存合成后的完整事实，不把通用 JSON Patch 或待执行合并指令变成第二事实源。

## 5. 两部分都要完成

### A. 档案内容

先建立覆盖清单，明确“大部分常见物品”的分母和完成状态。以现有 2014 / SRD 5.1 内容为基线，至少逐类清点武器、护甲/盾牌、弹药、冒险装备、工具、容器、照明/食物等补给、药水等常用消耗品；魔法物品按可复用效果与生命周期继续覆盖。

每类列出已建档、缺档及缺少的实际机械。普通物品也要有可实例化和持有的定义；带效果档案须有实际可执行的依赖，不能靠空效果或展示文案充数。不要只放三件演示道具就宣布“档案库完成”，也不要求穷举无限自创物品。

档案应有稳定身份和版本、来源、中文名称与别名、简短用途、完整定义和依赖。内容与加载机制分别可维护；实际存储位置按现有仓库和运行时选最简单方案，不预设新数据库或向量服务。

共用效果优先复用现役 Ability 定义与编译机制。治疗、伤害、状态、持续时间、充能与消耗等只在实际档案需要时补齐；不要另造一套由自然语言执行效果的引擎。

### B. KP 查找与差异填写

- 查找支持名称/别名及用途、效果、使用方式等结构特征。“充能治疗饰品”应能找到相关效果与结构，不能只做物品名称精确匹配。
- 先提供相关候选的简短可理解信息；选中后加载精确完整档案和依赖，并绑定同一裁决的冻结版本。不要把整个档案库或所有修改字段塞给每次调用。
- 查找结果用于提供可用模板，不能成为玩家行为的封闭菜单；找不到合适模板时继续已有完整创作路径。
- 完全复用、修改外观、修改机械、增加或替换效果应有明确填写边界。未改变的内容由服务端继承；能复用的效果无需模型重新抄写。
- 已验证变体应可在其合法作用域内再次引用。跨房间推广成全局模板不是本次必要条件；房间秘密、所有权和故事特有事实不可因此进入共享库。
- 具体采用现有 schema 选择阶段、已有检索接缝或新增受控调用，由实际入口决定；需要额外 Provider 调用时按现有预算与规格核对，不能无界扩循环。

## 6. 实现顺序及完成标准

1. **确认接缝和范围**：写出能力合同、逐类内容覆盖清单、代表性矩阵，枚举查找/冻结/填写/合成/Rules/Room/投影的真实入口、直接消费者和持久化边界。完成标志是明确缺口与改动链，不能只列文件名。
2. **完成通用纵切**：同一机制同时跑通现有档案直接复用及带差异生成；从真实本地行动接口到持久化和使用结果闭合。源码测试夹具可固定名字，生产分派不得按演示物品名称写专用分支。
3. **补齐档案覆盖与变化维度**：按清单铺内容，保证结构不同的样例走同一机制，实际依赖闭合。跨物品类型复用效果时检查目标、使用成本、充能及装备关系，而不是只换显示名称。
4. **验证填写确实减负**：捕获真实构造的模型请求与提交参数，展示“完整档案”和“引用＋差异”需要填写的差别；比较同场景输出字段或序列化体积，若有真实模型 token 再单独报告。只有展示变短、内部仍让 AI 重抄整份定义，不算达标。
5. **形成开发回执**：记录已覆盖类别、实际可调用链、定向验证、真实 Provider 证据及剩余内容缺口。库里有数据、Rules 可接受一个手写对象、某个模型输出能解析，均不能独立作为完成证明。

## 7. 代表性验收矩阵

以下是建议验收样例，不是用户限定的物品名称或封闭范围。实施时合并为目标用例组，按实际直接影响选取拒绝与恢复检查，遵守 AGENTS.md 开发期检查上限。

| 场景 | 要证明的行为 |
| --- | --- |
| 现有普通物品直接取得 | KP 选择现有档案并创建实物，不重填定义；数量、位置、持有权正确 |
| 治疗药水改名并改变治疗量 | 只填写差异，继承未改字段；实际使用执行新骰式且只消耗一次 |
| 结构不同的带充能物品变体 | 从相关档案复用效果，修改使用/充能属性；正确继承、消耗和投影，不走药水专用分支 |
| 没有合适模板 | KP 仍能经完整创作合同提出合法新物品；检索未命中不等于世界中不存在 |
| 模板过期、未知字段或非法机械 | 在提交与首份权威随机前拒绝，无物品、资源或事件的部分成功 |
| 原档案已被实例引用，再生成变体 | 旧物品效果、数量、所有权和历史保持原状，新变体独立使用 |
| 重复提交、等待骰子与恢复 | 相关场景按现役待决流程继续；重试不重复建物品、扣资源或调用 Provider，恢复引用原冻结档案 |
| 权限与公开结果 | 库存/效果结果按 Viewer 可见，模板不会授予不存在的物品或公开未获知的秘密 |

跨层行为至少通过真实本地接口。需要真实模型证明“会查、会选、只填差异、能提交并使用”时，沿 [现有有界 DeepSeek 测试预算](vnext-production-todo.md) 执行，首个明确失败即保存证据并定位；真实调用不代替定向 Rules / 恢复验证。
