# KP Agent 系统拆解与行动链问题审计

> 状态：探索性审计，不是 SPEC、ADR 或已批准改造方案。
>
> 日期：2026-08-31
>
> 样例：玩家说“扔一块石头看看这扇门上有没有陷阱”。

## 1. 文档目的

烛帷的 AI KP 不是一次 LLM 调用，而是一套 Agent 系统：它观察经过权限裁剪的世界，理解玩家意图，提出结构化行动，交给 Rules 裁决，由 Room Durable Object 固化，再根据每位观察者的安全投影生成叙述。

当前项目的主要问题不是完全缺少这些局部能力，而是：

1. 核心能力、可靠性设施和完整 5e 规则广度混在同一认知平面，导致项目难以理解。
2. 多个局部系统已经存在，但一次自然语言行动未必能把它们组合成一条完整因果链。
3. 少数超大型文件集中承担过多职责，任何局部修改都需要理解很大的影响面。
4. 部分意图路由仍依赖中文关键词，玩家换一种措辞便可能得到不同的 Form 候选排序。

本文件记录当前系统边界、已经确认的问题、代码层推断、具体行动样例和建议验收条件。它不得覆盖 [SPEC 0001](./specs/0001-llm-kp-responsibility-contract.md)。

## 2. KP 最重要的能力

### 2.1 核心 Agent 能力

按产品价值排序，KP 最重要的能力是：

1. **理解自由自然语言意图**：区分玩家的目标、方法、对象、条件和可接受代价，而不是把玩家限制在菜单或关键词模板中。
2. **作出公平的可行性裁决**：决定直接成功、需要检定、高风险可行、缺少前提或违反世界规律；DC、风险和后果必须在骰面前固定。
3. **维护动态且连续的世界**：在开放留白第一次与行动、证据或机械相关时即时固化隐藏现实，之后不能为迎合剧情或骰点而改写。
4. **组合因果行动**：让一个自然语言行动可以包含事实固化、环境交互、资源消耗、检定、危险、观察和角色推断，而不丢失原始目标。
5. **区分真相、证据和知识**：世界真实成立的事实、角色感知到的证据、角色作出的推断和 NPC/文献的来源主张必须分别处理。
6. **在权威结果内叙事**：叙述应有节奏、氛围和人物感，但不得修改已经提交的骰面、事实、资源、状态或受众范围。

这些能力的最高合同见：

- [自由行动与可行性裁决](./specs/0001-llm-kp-responsibility-contract.md#5-玩家行动与可行性裁决)
- [检定、DC 与公正](./specs/0001-llm-kp-responsibility-contract.md#6-检定dc-与公正)
- [隐藏现实的即时固化](./specs/0001-llm-kp-responsibility-contract.md#7-隐藏现实的即时固化)
- [信息、证据、传闻与角色知识](./specs/0001-llm-kp-responsibility-contract.md#9-信息证据传闻与角色知识)

### 2.2 不可缺少的支撑系统

| 系统 | 最小职责 | 为什么重要 |
| --- | --- | --- |
| 身份、成员与角色控制权 | 从可信会话确定主体，服务端验证谁能控制哪个角色 | 否则玩家可以伪造 actor、越权行动或读取秘密 |
| Context 与安全检索 | 为 KP 提供当前场景、角色、NPC 有限知识、Canon、规则和故事锚点 | 没有可信观察，模型无法作出连续裁决 |
| Form 与行动语言 | 把模型提案限制为可验证、有限、无 authority 字段的结构 | 防止模型直接写状态、骰面或事件 |
| Rules `step/replay/project` | 校验机械、请求权威随机、产生事件和按 viewer 投影 | 让机械结果可执行、可重放且不泄密 |
| Room Durable Object | 保存每房间唯一活跃权威，原子提交行动、随机、事实、Receipt 和受众 | 防止重复掷骰、部分提交和第二事实源 |
| Viewer 投影与交付 | 每位角色只获得自己有权知道的证据与叙述 | 多人秘密不能只靠前端隐藏 |
| 虚构时间与 Activity | 让耗时行动、休整、NPC 计划和危险共用同一时间轴 | 保证世界持续运行，而非只响应当前玩家 |
| 定向行为评测 | 验证意图理解、公平性、秘密边界和完整因果链 | 规则校验无法证明所有叙事选择都合理 |

归档恢复、完整生产遥测、语音、富地图、完整物品面板和 5e 长尾规则很重要，但不等同于 KP 的最小智能闭环。它们应当围绕核心闭环分层，而不是混在同一主流程中。

## 3. 当前真实行动链

当前主链可以概括为：

```text
玩家自然语言
→ API 认证与公共 DTO
→ Room prepare：权限、幂等和冻结观察
→ Context/RAG：组装本次必要信息
→ 主 KP：选择并填写一个私有 Form
→ CausalActionProgram：确定性编译
→ Proposal Adapter：重新校验并绑定可信 actor/root
→ Rules step：机械、随机请求和事件
→ Room DO：原子固化 Canon、状态、Receipt 和 AudienceSnapshot
→ project(viewer)：生成每位观察者的安全证据
→ KP narration：只根据该受众的已提交投影叙述
→ UI：展示行动状态与叙述状态
```

## 4. 项目臃肿的主要来源

截至本次只读盘点，生产核心区域约 98,645 行，其中 Rules 占约 54.9%，Room 占约 17.2%，KP 占约 14.6%。这说明臃肿主要来自现役规则广度和少数巨型文件，不是大量可以直接删除的历史目录。

主要热点：

### 4.1 不能因为名称而删除的内容

- `v1`、`v2`、`v3`、`v5` 多数表示不同协议轴，不代表五套产品实现。
- 当前生产只注册一个精确 Runtime manifest 和一个 Rules interpreter；文件名中的旧数字不能作为历史代码证据。
- Rules 的绝大多数文件仍从生产入口静态可达，其体量主要反映当前产品承诺的规则广度。
- D1 与 Room DO 不是重复数据库：D1 保存房间目录、配置和权威归档，DO SQLite 才是活跃世界唯一权威。

## 5. 已确认或高度可信的问题

### P0-01：缺少异构能力的单次 RootAction 组合

当前已有：

- `materialization.v1`：固化动态事实或隐藏现实；
- `environmental-stunt.v1`：复用、创建或改变有限环境要素；
- `observe.v1`：获取和解释证据；
- `compound.v1`：表达有界多阶段行动。

但一个 Proposal 只能选择一个 Form。当前 `compound.v1` 的每个阶段都会编译为通用 `assessCausalStage`，最后执行 `joinCausalBranches`；它不能在同一图中嵌入 `materializeOpenFact`、专用环境原语和 `inspectFiction`。见 [compound 编译](../app/_runtime/lib/kp/causal-action-program.ts#L308)。

因此，“先固化门是否有陷阱 → 石头撞门并触发有限状态 → 获取感官证据 → 必要时解释证据”在概念上是一条行动，但当前代码没有一条清晰可证明的单 RootAction 组合路径。

影响：

- 系统可能只完成其中一段；
- 模型可能把组合行动过度简化为一次普通检定；
- 也可能先提交一次事实固化，再要求玩家重复原行动；
- 原子性、时间消耗、秘密投影和叙述语义容易断开。

### P0-02：隐藏真相、物理触发和信息获取容易被合并成一次检定

“有没有陷阱”是世界事实；“石头是否撞中”是动作结果；“机关是否响应撞击”由已固化触发条件决定；“角色是否听见轻响”才可能是感知结果。

如果把四者压成一次 Perception 或 Investigation：

- 骰点可能错误地决定陷阱是否存在；
- 没有反应可能被错误叙述为“没有陷阱”；
- KP 可能在骰后才补写触发条件；
- 聪明方法无法真实改变信息质量。

### P0-03：开放留白的随机固化无法自然继续后续动作

当前隐藏现实实现会先秘密冻结候选集，请求 Room 权威随机，再登记选中 Definition 与 CanonicalFact。见 [隐藏现实固化](../app/_runtime/lib/rules/v2/causal-actions.ts#L4109)。

这条路径在选中事实后完成自己的机械结果，没有明确自动继续到环境触发或观察阶段。若门的真相尚未定义且几个结果同样合理，当前系统能安全决定“门实际上是什么”，但不能据此证明同一句玩家行动会继续完成“扔石头测试它”。

### P1-01：自然语言 Form 路由对措辞敏感

当前路由使用中文正则产生 Form 排序信号。“观察”“查看”“检查”等会命中 `observe`，但样例中的“看看”不会直接命中。见 [Form 选择信号](../app/_runtime/lib/kp/v3-context-runtime.ts#L753)。

关键词只决定候选排序，不直接决定机械，因此尚未越过安全边界；但它仍可能导致：

- 同一意图换一种说法便得到不同候选集合或顺序；
- 模型在过窄 Form 中被迫表达组合行动；
- 中文口语、方言和省略表达的采用率下降。

### P1-02：普通场景道具的权威身份不清晰

样例依赖“一块普通石头”。需要区分：

1. 石头已经是场景中可见、可复用的对象；
2. 场景明确没有石头；
3. 场景对此留白，KP 判断出现普通石头是否合理；
4. 石头是需要精确追踪数量、位置或消耗的机械物品。

玩家一句话不能凭空召唤有利物件，但把所有普通道具都做成完整 ItemInstance 又会显著放大复杂度。当前缺少一条容易理解的边界：何时只是有依据的叙事 affordance，何时必须成为 EnvironmentFeature 或 ItemInstance，何时消耗后必须持续记录。

### P1-03：环境“攻击”语义不适合所有物理尝试

专用环境路径支持 `attack`、`check` 和 `direct`。其中 `attack` 必须引用角色拥有的权威攻击能力，并且目标环境状态必须存在 damage transition。见 [环境提案绑定](../app/_runtime/lib/room/durable-object.ts#L4050) 与 [环境 transition 校验](../app/_runtime/lib/rules/v2/combat-actions.ts#L3609)。

普通石头撞一扇近距离大门通常不需要攻击检定，也不意味着要对门造成伤害。若强行走 `attack`，可能因没有“投掷石头”能力或门没有 damage transition 而失败。更合理的语义通常是：命中门板直接成功，再判断该接触是否匹配陷阱触发条件。

### P1-04：系统只实现有限状态，不是通用物理引擎

[SPEC 0015](./specs/0015-private-form-context-rag-and-narration.md#11-kp-自定义动态战术环境与-area-hazard-纵切) 明确规定只执行版本化有限状态和 Rules primitive，不实现通用物理引擎。

因此系统无法从“石头撞门”自动模拟振动、门板受力、机关传动和声学。KP 必须先提出相关触发与状态语义，Rules 只能验证并执行已支持的有限结构。

这不是单纯的 Bug，但必须在架构上承认：语义建模质量仍属于 KP，Rules 只能保证执行合法性。

### P1-05：候选与权重的叙事公平性不能由 Rules 完全证明

隐藏现实的规则层可以验证：

- 候选集合完整且有界；
- basis ref 存在；
- 不包含骰面、选中项或 authority 字段；
- 候选在公开证据前冻结；
- 随机抽取使用冻结权重。

但 Rules 无法证明“为什么只有这些候选”或“权重是否真正符合场景”。这部分主要依赖 KP Prompt、上下文质量、行为评测和可审计先例。安全机制能够阻止骰后改写，却不能自动证明叙事判断优秀。

### P1-06：Room Durable Object 是权威核心，也是最大认知热点

`durable-object.ts` 同时承担权限、prepare、幂等、随机、Rules continuation、事务提交、投影、投递、归档和恢复。集中权威本身是正确边界，但九千余行使局部职责难以隔离理解。

拆解时应保留：

- 一个 DO；
- 一个活跃 WorldState；
- 一个原子提交边界；
- 一个权威随机来源。

可以拆的是 DO 内部协作者和纯逻辑模块，不能拆出第二状态权威或跨服务分布式事务。

### P1-07：协议校验安全但分散

Form、CausalActionProgram、lowered input、Proposal Adapter、Room binding、DO 和 Rules 都会检查版本、hash、字段和引用。这能 fail closed，但使一次合法 schema 修改常常跨越多个文件，错误也容易只表现为宽泛的 contract failure。

需要收敛的是验证事实源和诊断映射，而不是取消关键边界上的重新验证。

### P1-08：公开投影和 UI DTO 仍有较厚适配层

权威状态会先经过 `project(viewer)`，再经过桌面 allow-list adapter、transcript/delivery 状态和 UI DTO。秘密边界因此可靠，但任何显示字段变化都可能跨越 Projector、DO、Table adapter 和 UI。

当前 `table/authoritative.ts` 仍承担较大的 legacy-shaped DTO 适配。未来若 UI 能直接消费稳定的安全投影 DTO，可以减少重复塑形；这属于公共接口迁移，不能直接删除。

### P2-01：核心能力与可后置系统没有形成清晰产品层级

完整 5e 规则、归档灾备、语音、地图、富桌面、生产遥测和模型评测都出现在同一仓库。它们的重要性不同：

- 身份、单一权威、机械裁决、秘密投影、虚构时间属于产品骨架；
- 归档和遥测属于可靠性平面；
- 语音、地图和富面板属于适配/呈现平面；
- 完整 5e 长尾属于规则内容广度。

如果不先划分这些平面，“瘦身”容易误删不变量，或者继续在主循环里堆入非核心功能。

## 6. 样例行动的正确完整流程

### 6.1 场景假设

- 玩家角色站在门外几米；
- 地上确实有一块普通石头；
- 门已存在；
- 当前不在战斗或其他时间压力下；
- 玩家没有要求砸坏门，只想测试陷阱。

### 6.2 阶段与权责

| 阶段 | 决定者 | 正确结果 |
| --- | --- | --- |
| 理解意图 | KP | `goal=探查陷阱`，`method=石头撞击门板并观察` |
| 检查前提 | Canon + Room | 石头和门必须已存在，或按开放留白规则合法固化 |
| 固化门的真相 | KP 提案；Rules 校验；DO 随机/提交 | 在撞击产生证据前确定是否有陷阱及其触发条件 |
| 石头是否命中 | KP 决定 direct/check；Rules 执行 | 近距离命中大门通常 direct，无意义失败则不掷骰 |
| 是否触发 | Rules 执行已冻结定义 | 只有撞击满足触发条件时才改变陷阱状态 |
| 获得什么证据 | `project(viewer)` | 只给角色真实听到、看到或感觉到的信息 |
| 是否理解细节 | KP 决定 direct/check；Rules 掷骰 | 明显证据直接获得，细微证据才检定 |
| 叙述 | KP Narration | 只表达已提交投影，不能把“无反应”说成“绝对安全” |

### 6.3 一个合理的隐藏候选示例

若已有事实无法唯一推出答案，KP 可以基于当前地点、势力、历史与自然规律提出：

1. 门没有陷阱；
2. 门把内有毒针，转动门把或插入工具时触发；
3. 门板有震动触发的警铃，受到明显撞击时触发。

候选和权重必须在石头撞门前冻结。若可信随机选中第 2 项，石头撞击门板并不会触发毒针。

### 6.4 正确叙述示例

> 石头砰地撞在门板上，又滚回地面。没有箭矢、火光或明显的机关声。你只能确认这次撞击没有触发可见反应；这不足以证明门把、门锁或门槛没有机关。

该叙述保持了三个边界：

- 事实：门把内确实有尚未触发的毒针；
- 证据：撞击门板没有产生明显反应；
- 推断：玩家只能排除一部分“撞击触发且有明显表现”的机关，不能断言门安全。

## 7. 当前代码对该样例的实际覆盖

### 已能覆盖

- 自由文本进入私有 Form 选择；
- 已存在 EnvironmentFeature 的复用和状态转换；
- `direct`、`check`、`attack` 三类环境 activation；
- 隐藏现实候选冻结、可信随机和 Canon 登记；
- Rules 机械结果和 Room DO 原子提交；
- 按 viewer 投影与提交后叙述；
- 明显证据不必强制检定的产品合同。

### 尚不能证明一次完成

- 开放留白中先随机固化门的隐藏现实，再立即继续石头碰撞；
- 在同一 RootAction 内把专用环境 transition 的结果继续交给一次细微信息检定；
- 无反应时生成严格受限的“排除了什么、仍不能排除什么”的结构化知识增量；
- 将普通石头作为叙事道具使用，同时在需要时正确升级为被追踪对象；
- 不受“看看/检查/观察”等具体措辞影响地稳定选择同一语义路径。

上述结论来自静态代码与规格对照，尚未以真实模型调用跑通该精确句子的端到端轨迹。

## 8. 建议的最小验收矩阵

这句话适合作为下一轮能力开发的代表性纵切，而不是只添加一个“石头”专用分支。

| 场景 | 隐藏现实 | 预期 |
| --- | --- | --- |
| 已存在、撞击触发 | 门板受撞会触发警铃或飞镖 | 石头命中后触发；明显证据直接投影；陷阱状态持续变化 |
| 已存在、非撞击触发 | 毒针只在转动把手时触发 | 石头无明显效果；不得宣布“没有陷阱” |
| 开放留白、多种结果合理 | 无陷阱、把手陷阱、撞击陷阱均合理 | 先冻结候选并可信抽取，再在同一行动继续碰撞和观察 |
| 命中本身有不确定性 | 远距离瞄准细小锁孔 | 骰前固定检定与失败代价；骰点只决定是否命中，不决定陷阱存在 |
| 普通石头明确不存在 | 场景已固化为无松动物件 | 世界内说明前提不足，不凭玩家一句话创造石头 |
| 反应细微 | 撞击产生很轻的内部咔嗒声 | 真相和触发先固定；检定只决定角色是否听见/理解细节 |
| 多人观察差异 | 只有靠近门的角色能听见轻响 | 每位 viewer 得到独立投影，不向全桌泄露 |
| 幂等重试 | 网络断开后用同一 submission 重试 | 不重新固化、不重掷、不重复触发或消耗 |

## 9. 建议的收敛方向

以下只是架构方向，实施前仍需形成能力合同和代表性测试：

1. **让 `compound` 成为真正的异构因果图**：能组合事实固化、环境作用、检定、观察、Activity 和 NPC 交互，而不是只有通用阶段描述。
2. **建立显式知识增量模型**：机械结果应能表达“观察到什么”和“该证据支持/排除什么”，Narration 只负责自然语言表达。
3. **弱化关键词路由的决定性**：先提取 goal/method/target/stakes，再根据语义和权威状态选择 Form；关键词最多用于低风险排序。
4. **裁定普通场景道具层级**：定义 narrative affordance、EnvironmentFeature 和 ItemInstance 的升级条件，避免既凭空创造，也把每块石头做成重型实体。
5. **拆分巨型实现文件，但保持权威边界不变**：优先拆 DO 内部协作者、Rules command family 和 UI 独立职责，不增加第二状态源或第二裁决路径。
6. **收敛协议事实源和诊断**：每个版本/hash/schema 只定义一次，在各信任边界复用相同验证器，并把失败定位到具体层级。
7. **先保留核心纵切，再决定规则广度**：用少量完整场景证明 Agent 闭环，再评估完整战斗、物品、地图和语音的产品优先级。

## 10. 需要后续明确的产品决策

1. 一个清晰的多阶段自然语言意图，是否必须在一个 RootAction 内连续完成，除非遇到真正需要玩家选择的 Pending？
2. 普通、无机械优势的场景道具可以由 KP 直接确认为叙事 affordance，还是一律必须先 Materialize？
3. “没有反应”应如何结构化为有限知识，而不是只依赖 Narration 谨慎措辞？
4. 隐藏候选和权重的公平性，采用哪些行为评测、先例与审计证据保证？
5. 第一阶段瘦身要保留的规则纵切有哪些，哪些完整 5e 长尾能力可以后置？

## 11. 当前结论

烛帷已经拥有一套安全边界较完整的 Agent 基础设施，但“能力数量多”不等于“自然语言行动闭环完整”。当前最应优先解决的不是继续增加 Form 或领域系统，而是让已有的事实固化、机械作用和知识投影能够围绕一个玩家目标组成单一、可验证、可重放的 RootAction。

“扔一块石头看看门上有没有陷阱”应成为这项收敛工作的第一个端到端验收用例。
