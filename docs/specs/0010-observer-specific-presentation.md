# SPEC 0010：观察者专属呈现与当前回应投递

- 产品：烛帷
- 适用规则：D&D 5e 2014 / SRD 5.1

## 1. 继承关系与变更规则

本规格实现 `SPEC 0001` 对角色知识、秘密投影、多人聚光灯、叙述、裁决说明和错误更正的冻结要求，不修改、缩小或取代 `SPEC 0001`。任何冲突都以 `SPEC 0001` 为准。

本规格裁定的是可执行呈现协议，不把叙述文本变成正史，也不建立新的状态权威。结构化世界事实、角色知识、来源、关系和更正由 Room Durable Object 中的权威事件永久保存；KP 的具体措辞只用于当前回应投递及原冻结 ViewerKey 的亲历记录。

本规格不授权：

- 向玩家提供跨观察者、可补取、可搜索或可由事件重建的完整 KP 旁白、模型消息或语音转写历史；
- 以可靠送达为名建立聊天记录、消息队列、D1 叙述归档或第二套事件日志；
- 让房主、队长、页面、语音 Adapter 或日志系统扩大观察者权限；
- 根据后来入场、后来入席、后来加入队伍或后来获得角色控制权，回补过去的回应；
- 删除现有语音输入能力，或为本协议创建新的 KV、R2、Queue 或其他持久化资源。

### 1.1 2026-08-28 用户修订：亲历对话可回看

用户已明确裁定：角色当时实际在场并取得的对话，离开场景、刷新或稍后回到该场景后仍应可查看；只有当时不在场、没有观察资格的角色才没有相应记录。本修订在“不可回看”“无历史 UI”与固定单槽正文删除等条款发生冲突时优先，且不扩大任何观察者权限。

实现必须把可靠投递槽与亲历记录分开：

- `DeliveryFrame` 仍是每个 ViewerKey 的唯一当前可靠投递槽；
- Room DO 另按 `principal + character` ViewerKey 保存亲历记录，只能由提交时冻结的 AudienceSnapshot 决定谁获得其专属 KP 回应；
- “亲历”以文本成功发布到冻结 ViewerKey 为界：ACK 只证明呈现并清空当前槽，不是取得历史资格的前提；从未成功发布的候选、失败输出和安全撤销内容不进入记录；
- 行动者的原始意图只进入行动者自己的亲历记录，不因同场而广播其可能包含的秘密意图；其他在场者保留其各自实际收到的观察者专属回应；
- 待决问题只进入每个冻结 `pending controller` 自己的 ViewerKey；多人同意不得把受邀者的问题写给发起者。控制权转移后，新控制者不继承旧 ViewerKey 的其他记录，但其实际查看或回答的仍开放问题必须在回答前补入自己的亲历记录；
- 记录绑定当时地点；离场、回场、刷新、断线和普通 DO 重启不删除，后来入场者不得补取；控制权转移或继任 principal 不继承原 principal 的记录；
- ACK 或新回应覆盖只改变当前可靠投递槽，不删除已经亲历的记录；安全暂停、权限撤销和尚未成功发布的回应不得形成可回看副本；
- 亲历记录不是 WorldEvent、机械正史或第二套状态权威，不参与 replay，也不写入 D1 事件归档；更正必须追加明确的新记录，不静默改写旧话；
- 本修订上线前已经被覆盖且只剩哈希 tombstone 的旧正文不得猜测或从事件伪造，历史从仍可取得的当前帧及上线后的新回应开始保存。

因此，下文“完整 KP 旁白历史”专指跨观察者、可补取或可重建的全局历史；本修订允许的 ViewerKey 专属亲历记录不属于该禁止范围。

## 2. 产品结果

玩家只收到其角色在相应世界时刻能够观察、其可信 principal 有权读取的回应。个人线索默认保持私有，直到角色通过同一权威行动事务在世界内分享，或其他角色独立取得相应证据。

玩家界面可以持续查看当前结构化 Read Model，以及同一 ViewerKey 已亲历的有界对话记录，包括其角色已经合法获得的知识、可见世界事实、资源、待决输入和脱敏 Receipt；但不能全文搜索、按旧 ID 重建，或补取从未向该观察者成功发布的 KP 旁白。

可靠投递采用固定单槽协议：

> 每个 ViewerKey 至多保存一个未确认的 DeliveryFrame；刷新、重复轮询、断线和 Worker 重启恢复同一 deliveryId；ACK 或新回应只清空/覆盖当前槽，成功发布的文本进入同一 ViewerKey 的亲历记录；结构化事实与角色知识不受覆盖或 ACK 影响。

## 3. 领域语言

**可信 principal（Trusted Principal）**：由已认证会话得到的用户身份。请求体中的 `userId`、`principalId`、`viewerId` 或 `actorId` 不能建立权限。

**观察者主体（Viewer Subject）**：投影所代表的主体，可以是受控玩家角色、NPC、KP 主持视角或 Room DO 内部视角。普通玩家不能请求 KP、NPC 或内部主体。

**ViewerKey**：`roomId + trustedPrincipal + authorizedViewerSubject + viewerRole` 的稳定组合。它由服务端按当前席位和控制权构造，不由客户端自报。同一 principal 的多个浏览器设备共享同一个 ViewerKey；同一 principal 合法控制多个角色时，每个角色主体具有不同 ViewerKey。

**虚构在场（Fictional Presence）**：观察者主体在结果提交时位于能够通过感官、能力、通信媒介或已固化特殊联系接触该结果的世界位置。仅仅是房间成员、房主、队长、网络在线或正在看页面，不构成虚构在场。

**观察资格（Observation Entitlement）**：由虚构在场、感官与能力、遮挡、知识、控制权、内容权限和结果的公开级别共同决定的读取资格。

**AudienceSnapshot**：世界或机械结果提交时，由统一 projector 根据冻结状态确定的具体 ViewerKey 集合及各自 `projectionHash`。它绑定 `eventRange`、`activeBranchId`、相关作用域版本和呈现策略版本；之后不能扩大。

**个人线索（Personal Clue）**：只由一个角色或一组明确角色取得的感官证据、来源主张、角色推断或其他结构化知识。它不是房间级布尔标记，也不因为实物被移动而消失。

**知识所有者（Knowledge Holder）**：权威状态中持有某项结构化知识的角色或 NPC。知识属于世界内主体；其当前合法控制者可以查看该主体的当前知识投影，但不能因此读取先前控制者收到的叙述帧。

**KnowledgeShare**：角色通过说、写、展示、演示、传讯或其他世界内手段，把具体内容传播给冻结接收者的一次权威行动。它必须记录来源、内容粒度、媒介、接收者、时间、地点和因果依据。

**DeliveryFrame**：面向一个 ViewerKey 的当前、可确认、非正史呈现载荷。它绑定已提交结果和专属投影，可以包含文本以及同一内容的语音呈现元数据；它不是 `WorldEvent`、角色知识、聊天消息或 D1 归档记录。

**ACK**：相应可信 principal 明确确认已经收到当前 DeliveryFrame 的 UX 操作。ACK 不代表角色同意、接受、放弃、行动、结束回合或推进虚构时间。

**当前帧不可重取（Non-retrievable Delivery）**：DeliveryFrame 在 ACK、被同一 ViewerKey 的新回应覆盖、权限撤销或安全失效后，不能再通过旧 `deliveryId`、Receipt、实时流、轮询、错误、候选项、日志、语音或归档取得；成功发布且未被安全撤销的文本只可作为原 ViewerKey 的亲历记录保留，音频、TTS 资产、模型 Prompt 和逐字转写不随之归档。

## 4. 观察资格与 Audience 冻结

### 4.1 谁能够观察当前回应

一个玩家 ViewerKey 只有同时满足以下条件才进入 AudienceSnapshot：

1. principal 在结果提交时是合法房间成员并具有相应观察者主体的控制或查看权限；
2. 观察者主体在虚构上位于能够接触结果的位置，或存在已固化、当前有效的远程感知/通信渠道；
3. 该主体的感官、能力、状态和遮挡允许取得相应信息；
4. 结果的可见性策略允许向该主体公开；
5. 内容安全或私人窗口规则没有进一步收窄投影。

网络断线、页面关闭或设备休眠不改变虚构在场。一个断线但角色仍在场且有观察资格的玩家可以进入 AudienceSnapshot，并在恢复连接后取得其仍为当前的 DeliveryFrame。

角色位于另一地点、尚未加入场景、没有相应感官、只拥有房主或队长身份，或者仅能从 KP 全知上下文推知结果时，均不得进入 AudienceSnapshot。

### 4.2 Audience 在提交时冻结

AudienceSnapshot 必须与产生可叙述结果的权威提交绑定。Audience 不能由 LLM、页面、投递器或读取时的当前成员列表决定。

以下变化不能把新 ViewerKey 加入旧 AudienceSnapshot：

- 后来进入该地点或与队伍会合；
- 后来入席、加入房间、接管角色或成为房主/队长；
- 后来获得远程感知能力；
- 后来通过分享获知相关结构化内容；
- 后来因更正以外的原因获得更高权限。

后来入场者可以从当前仍然存在的世界状态形成新的感官证据，例如看到已经烧毁的门；这是一项新的观察事件，不是旧回应回补。短暂声响、已结束的对话和旧旁白不能仅因后来进入同一地点而重现。

席位或控制权转移后，新 principal 可以查看所控制角色当前合法持有的结构化知识，但不能取得该角色以前的 DeliveryFrame。原 principal 一旦失去成员或控制权限，即使曾在 AudienceSnapshot 中，也不能再读取尚未确认的帧；相应槽位必须安全失效或清除。

## 5. 个人线索的取得与私有期

### 5.1 何时保持私有

下列信息默认成为对应角色的个人线索：

- 只有该角色通过位置、感官、被动能力、检定或特殊能力取得的证据；
- NPC、文献、梦境、心灵联系或私人窗口只向该角色传达的来源主张；
- 只有该角色有资格形成的角色推断；
- 玩家为自己角色作出的秘密选择及其尚未公开的结果；
- 内容安全协议明确限定给请求者的现实玩家私人信息。

同一结果如果被多个角色在提交时直接观察，则每个角色分别获得自己的知识事件；这不是一份房间全局线索。角色共同看见一段墙上文字，可以分别取得相同内容，但其来源、完整度和理解层级仍可不同。

个人线索的私有期没有自动到期。以下事实不会自动公开它：

- 角色与队伍重新会合；
- 场景、章节或现实团次结束；
- 玩家刷新、重连或离线；
- 房主、队长或其他玩家请求查看；
- 持有线索的实物被转移、毁坏或遗失；
- 原角色死亡或退役。

角色死亡、退役和继任角色不会自动复制知识。跨角色继承必须由长团生命周期规格允许的世界内来源或明确继承事件建立；在该规格落地前默认不继承。

### 5.2 谁能读取个人线索

个人线索的结构化内容只投影给：

- 该知识所有者的当前合法控制者；
- 按有限知识需要使用该信息的相应 NPC Viewer；
- 可信服务端内部的 KP Viewer 和 Room DO 内部 Viewer；
- 经世界内分享后成为新知识所有者的角色或 NPC。

KP Viewer 的可见性不授权把信息写入玩家回应。房主、队长、同队成员或角色原控制者没有默认读取权。

## 6. 世界内分享协议

### 6.1 分享必须是一项权威行动

玩家分享个人线索时，客户端仍只提交自然语言意图或待决回答。Room Action Module 从可信会话确定 principal 和受控角色，KP 判断媒介、可行性、耗时、是否会被听见或中断，Rules Module 验证必要机械，Room DO 原子提交传播事件及其时间、位置和后果。

分享不能由页面直接把接收者的知识数组补齐，也不能通过桌外“转发 KP 消息”按钮绕过世界。若玩家确实在现实桌外把秘密告诉了另一玩家，产品仍不能把接收者角色视为已经知道；角色知识只由世界内事件改变。

### 6.2 分享内容和范围

每次分享必须冻结以下内容：

- `sourceKnowledgeRef` 或被展示的 Artifact/文献/世界事实引用；
- 分享者实际表达或展示的内容；
- 内容类型：精确转述、摘要、来源主张、推断、感官展示或实物转移；
- 媒介及其可达、可听、可见、可拦截条件；
- 具体接收角色/NPC 集合；
- 分享发生的虚构时间、地点和相关因果范围；
- 接收者取得的知识层级、来源和可信度。

支持的接收范围可以是：

1. 明确点名的一个或多个世界内主体；
2. 当前地点内能够感知该次交流的全部主体；
3. 当前小队或当前房间中满足指定世界内通信条件的主体；
4. 经已固化广播、书面材料、传讯或公开展示实际覆盖的主体。

`全队`、`所有在场者`、`房间里的人` 等集合必须在分享提交时解析为具体世界内主体 ID，并按感官、位置和媒介过滤。以后加入该集合的角色不自动获得知识。

角色声称“门后有宝藏”时，接收者获得带说话者、时间和依据的 SourceClaim，不自动获得门后真实情况。展示火药残留可以让有资格的接收者取得新的 SensoryEvidence；递交遗嘱会改变实物持有关系，但不会撤销分享者已经读过的知识。

### 6.3 分享一律不追溯回应

KnowledgeShare 从其提交时开始影响接收者知识，默认不追溯。接收者可以在之后的 Read Model 中看到新获得的结构化知识及其允许公开的来源，但不能取得：

- 分享者最初收到的 KP 旁白；
- 分享发生前只投递给分享者的 DeliveryFrame；
- 分享者没有表达的额外证据、推断或秘密上下文；
- 同一线索过去的语音、逐字转写、候选项或错误信息。

若分享者希望补充更多内容，必须再次通过世界内行动表达；系统不能从旧叙述文本自动扩写。

## 7. 统一 Read Model 与 projector

`project(module, source, viewer)` 是所有观察者专属领域内容的唯一 Interface。页面、Room Action Module、KP 结果叙述、NPC 决策、快照、增量、结构化知识、Receipt、待决输入、候选项、错误说明和玩家可见活动日志都必须从同一个内部 projector 得到。

统一 projector 必须：

- 从可信服务端构造的判别式 Viewer 取得权限，不接受裸 `viewerId`；
- 同时应用角色知识、感官、位置、AudienceSnapshot、控制权、分支、规则版本和内容安全策略；
- 对快照、增量、错误和候选项采用同一字段可见性，不能在某一路径另写脱敏逻辑；
- 拒绝缺片、断序、哈希不符或版本不匹配的增量，而不是退回原始事件；
- 永不把原始 WorldEvent、KP Viewer、模组真相或内部 flags 交给普通客户端；
- 让同一有效值来源同时服务机械裁决和投影，页面不另算资源、位置、效果或知识；
- 在角色控制因死亡或退役结束后，仍由可信 lifecycle Viewer 经同一 projector 产生最小 `successorRequired` Read Model；服务层和页面不得手写继任视图；
- 由 Rules projector 产出 `restRecoveryOptions` 等机械候选及其上限、资格和预算；页面只能消费并冻结玩家选择，不得重算恢复机械；
- 生成 `projectionHash`，使 DeliveryFrame、Receipt 和重试绑定准确观察者状态。

Read Model 可以包含：

- 当前可见世界事实和感官信息；
- 自己角色的精确资源、状态、物品和结构化知识；
- 被授权的待决输入和候选项；
- 脱敏、无叙述正文的 Receipt；
- 当前 DeliveryFrame 或其 `none/acknowledged/superseded` 状态；
- 已公开且该角色已经取得的裁决更正。

Read Model 可以保留结构化线索簿、角色知识及允许公开的来源链，因为它们是权威世界事实；观察响应还可以附带该 ViewerKey 已成功取得的亲历文本。任何投影都不能保存或重建其他 ViewerKey 或未成功发布的 KP 措辞、模型 Prompt、音频或转写历史。
